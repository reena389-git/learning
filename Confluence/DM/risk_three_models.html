Three Models for Risk Data — and the Conformance That Holds Them Together

Canonical · Analytical · Semantic · Conformance — what each one does, and why your reports are only the beginning

This note is for the risk application teams — CCR, Market Risk, Valuation Services, RCS, Product Control, and the others currently producing risk metrics. Today, each app calculates results and publishes them as reports or extracts. Those reports are valuable, but they are a small fraction of what a complete risk data architecture requires. This document lays out three models — Canonical, Analytical, and Semantic — that the data needs to be expressed in, plus a fourth layer, Conformance, which is the discipline that binds the physical world to the logical model.

The example used throughout is CCR / Collateral — counterparty exposure, agreements, trades, collateral — but the same three-model structure applies to every risk sub-domain.

The Canonical Risk Data Model

The logical model of risk concepts — independent of any one app, report, or platform.

What it is

The canonical model describes risk as a set of business entities and the relationships between them. It is a logical model — normalised, 3NF or close to it — that answers the question: "what are the things in this domain, and how do they relate?"

For CCR / Collateral, the entities are concepts like Counterparty, Agreement, Netting Set, Trade, Collateral Position, Issuer, Exposure Measurement. Each entity has its own attributes and a defined relationship to other entities (a Counterparty has many Agreements; an Agreement governs many Netting Sets; etc.).

What it is not

The canonical model is not a physical database, not a report layout, not an app's internal schema, and not a star schema for BI. It is the shared logical definition that every physical implementation refers back to. Two different apps may store Counterparty data in physically different shapes, but if both are conformant with the canonical model, they mean the same thing when they say "counterparty credit rating" or "ultimate parent."

What it gives you

  • A shared language. When CCR, XVA, and Collateral Management all say "Counterparty," they mean the same thing — same identifier, same parent hierarchy, same rating fields.
  • A stable spine. The canonical model changes slowly. Apps and reports change quickly. Anchoring to the canonical model means downstream consumers aren't disrupted every time an app changes its internal schema.
  • A target for integration. Data from multiple apps can be conformed to canonical entities, enabling cross-app analytics that aren't possible when each app's data sits in its own silo.

Where your reports fit

Most reports today are not conformant with a canonical model — they are app-specific outputs with app-specific names, structures, and definitions. The canonical model is the target shape these outputs need to be aligned to over time, so consumers (analytics, regulatory reporting, business users) can combine them without re-discovering definitions every time.

Why this matters

  • Without a canonical model, every consumer of risk data has to learn each app's vocabulary separately, and reconciliation across apps becomes manual.
  • The canonical model is the only layer where cross-app integration semantics can be defined once. Skipping it pushes that work into every analytics product downstream.
  • This is logical, not physical. It does not require migrating any system. It is a reference others align to.

Logical model → physical model → distribution format and API

There is a common confusion that runs through almost every conversation about how to publish data: that "I'll just use an API" or "I want JSON, not joins" or "give me a snowflake" or "a canned report works for me" are alternatives to data modelling. They are not. Each of those is a physical implementation or distribution choice sitting on top of (or, more often, in the absence of) a logical model. Talking about APIs without talking about what the API is exposing is talking about delivery without talking about content.

The clarifying picture is three layers, not two:

  • The logical model — the entities, attributes, and relationships that describe the domain in business terms. This is the conformed artefact. It is the source of meaning. Independent of any database, any file format, any API design.
  • The physical model — how the logical model is materialised for storage and querying. Star schema, snowflake, denormalised flat, OBT, document store, key-value store. Each is a legitimate physical realisation of the same logical model, optimised for different consumption patterns. The physical choice trades off integrity, storage, query simplicity, and schema-evolution flexibility — but it does not change what the data means.
  • The distribution format and protocol — including APIs — how the physical data gets delivered to consumers. A REST API is a protocol (web-based request/response). JSON is a distribution format (how data is serialised in transit). The two are pairs: REST/JSON, GraphQL/JSON, SOAP/XML, database connection/SQL result-set, file drop/CSV, streaming pipe/Avro. The distribution layer chooses how the data leaves the system, not what it means.

A consumer who says "I want JSON" is making a distribution-format choice. A consumer who says "I want an API" is making a protocol choice. Neither of these tells you anything about the underlying logical model the data represents — and neither replaces the need for one. An API delivering JSON is the consumer-facing surface; behind it, there is still a physical store, and behind that, there is still (or should still be) a logical model. The joins that the consumer was hoping to avoid by "just using an API" still happen — they happen inside the service that backs the API, or they happen eagerly by denormalising into the JSON shape ahead of time. The work doesn't go away; it just moves.

Industry grounding for this picture

The layered approach above is not unusual. Large banks have been building it under regulatory pressure for over a decade. BCBS 239 (the Basel risk-data aggregation standard) explicitly requires consistent counterparty and product identification across risk systems. FRTB (the market-risk overhaul) requires consistent identification of trades, instruments, and risk factors across the bank's models. The Canadian regulatory regime around credit risk reporting (CDR) imposes similar demands. The CDO function building the enterprise canonical model is the standard institutional response to these requirements.

The Data Contract band is more recent as a term-of-art — it became standard vocabulary in the data-mesh and data-product literature roughly from 2022 onward. The concept it captures was always needed; the explicit name made it easier to discuss as a separate artefact with its own owner.

Where APIs sit in this picture

APIs are in the bottom band, alongside files and streams. This placement matters. There is a common instinct to treat APIs as their own architectural layer — as if "I'll use an API" or "I want JSON, not joins" were modelling decisions. They are not. An API is a delivery channel. What gets delivered through it — the entities, the attributes, the relationships, the semantics — depends entirely on the layers above the distribution band. The choice of API as the channel does not exempt any of the upper layers from being built.

The CMOS Collateral JSON shown on this page in Figure 1b is a worked example of exactly this point. The JSON is delivered by an API; the JSON itself is a physical representation — a hierarchical serialisation of the collateral domain for transport. But when the JSON is exploded, what comes out is a logical model: Agreement, Counterparty, Trade, Margin Call, Asset Holding, Asset Movement, Dispute — entities and relationships that exist independently of how the data happens to be carried. The JSON did not invent the model; it carried it. The same logical model could have been delivered via a relational database query (JDBC + SQL), a CSV file drop (SFTP + CSV), or a streaming feed (Kafka + Avro). The choice of API + JSON was a delivery decision; the model underneath stays the same.

This is the point worth landing: any physical representation — star schema, snowflake, denormalised flat, JSON document, streaming event — is downstream of one logical model. The logical model defines what entities exist and how they relate. The physical representation is the choice of how to materialise them. APIs are how a physical representation reaches the consumer.

The reframing: stop arguing about "API vs database" or "JSON vs table." Start asking what the logical model is, what physical representation suits the consumer, and which delivery channel serves their consumption pattern. All three answers can be different; what cannot vary is the underlying meaning of the data. Conformance lives in the logical model; everything below it is local engineering choice.

The report and the three models behind it

A specific lens on the same architectural picture is worth drawing out separately, because it is the most common way the modelling argument fails to land with stakeholders. The report is what most consumers see today. Looking at the report alone, the number on the screen appears to be the whole picture. It is not. Several layers of context that the report needs are not carried in the report itself — they live in artefacts the report depends on but does not contain.

The three models supply that missing context. They are not derived from the report; the report is incomplete without them. The direction matters: meaning flows up from the three models to the report, not down from the report to the models.

The Analytical (Star) Model

Risk metrics organised for slicing, aggregating, and combining — built from your reports.

What it is

The analytical model takes the measures your risk apps produce and organises them into a star schema optimised for analytical queries. It has two parts:

  • Fact tables — one or more, each holding measures at a specific grain. For CCR, a fact might be fact_exposure_daily at the grain of netting set × date, holding measures like base exposure, PFE, and EAD.
  • Dimension tables — descriptive context that surrounds the facts: counterparty, agreement, trade, date, currency, asset class, etc. Each dimension is wide and denormalised for query speed.

What "grain" means and why it matters

Every fact table has a grain — the level at which one row of data corresponds to one event or measurement. For exposure, the grain is typically netting set × date: one row per netting set per measurement date. The grain is set by the risk app when it calculates the measure; it cannot be reconstructed later if it is not declared.

Once the grain is declared, downstream analytics can aggregate up from it (e.g., sum to counterparty level) but never down (you cannot recover trade-level exposure from a netting-set-level fact, because the netting calculation has already been applied). The grain is a contract.

Where your reports fit

Your reports today carry measures and grain — but typically without declaring either explicitly. A report titled "Counterparty Exposure by Region" implicitly defines:

  • A measure (counterparty exposure) with an unstated aggregation rule
  • A grain (typically counterparty × date) that the user must infer
  • A set of dimensions (counterparty, region, date) embedded as columns

The analytical model formalises all three: measure, grain, dimensions. Your report becomes a fact table plus its surrounding dimensions, with each part declared explicitly.

Why dimensions get defined once and reused everywhere

The single star above shows one fact surrounded by its dimensions. The point of the dimensional model only becomes fully visible when several facts share the same dimensions. Conformed dimensions are dimension tables that are defined once and reused across every fact that needs them. A counterparty means the same thing whether it appears against exposure, against a margin call, against a settlement, or against a dispute — because all four facts point to the same dim_counterparty.

This is what makes cross-fact analysis safe. Slicing exposure by counterparty rating and slicing margin calls by counterparty rating produce numbers that combine because the rating comes from one governed source. Without conformed dimensions, each fact carries its own version of "counterparty" and cross-fact slicing produces silent inconsistencies.

Figure 2b — Conformed dimensions: defined once, referenced by every fact. The reuse is what makes cross-fact analysis trustworthy.

The economic point is straightforward. Each conformed dimension is built once and governed centrally. Every fact that needs it points at it. When a new fact is added — credit limits, collateral movements, breach events — it joins to the same dimensions and inherits their consistency without any additional conformance work. The investment in defining a dimension well pays back every time another fact references it.

Representing classification hierarchies — the asset class pattern

A subtlety that comes up often when modelling dimensions: the same domain can be carved into different hierarchy shapes depending on who is asking. Take asset class as the running example. Asset class is naturally a two-level hierarchy — asset_class at the top, product_type underneath. But different lines of business legitimately use different hierarchy shapes for this domain. One line of business might use a coarse hierarchy with three product types under Bond; another might use a fine-grained hierarchy with twelve. The product types defined by each are different, and the granularity of the breakdown is different.

Both hierarchies are correct in their context. One isn't more right than the other; they serve different analytical needs. A conformance approach that picks one hierarchy and forces it on everyone loses information that some consumers need; one that lets each consumer maintain its own hierarchy in isolation loses the ability to compare across lines of business at all.

The conformed answer recognises that the terminology — the column names asset_class and product_type — can be shared across lines of business even when the values under those columns are organised into different hierarchies. The dimension carries the hierarchy variant explicitly as a hierarchy_rule column, with an owner. A single instrument can then appear under multiple hierarchy rules — once for each line of business's view — with the asset class and product type values appropriate to each view. Consumers bind to the hierarchy rule that matches their purpose; the dimension does not force a choice between views.

Figure 2c — Asset class hierarchy with rule variants. Each line of business's hierarchy lives as its own set of rows, distinguished by hierarchy_rule. The terminology conforms; the values and the shape they describe do not have to.

The dimension table structure

The dimension carrying this pattern looks like the following. A single instrument has multiple rows in the dimension — one per hierarchy_rule it has been classified under — with the asset class and product type values appropriate to each rule.

Figure 2d — The dim_asset_class table structure. One row per (instrument × hierarchy_rule), with the rule owner and effective dates explicit. Consumers filter on hierarchy_rule to bind to the view they need.

The compound primary key — (instrument_id, hierarchy_rule, effective_from) — matters. Without it, queries that don't filter on the rule would silently multiply rows. Every consumer query against this dimension is expected to filter or group by hierarchy_rule, and the metadata declares this requirement. The dimension does not let a consumer accidentally produce a count that mixes hierarchies, because the mixing would be visible in the row counts.

The same pattern applies to any dimension where multiple legitimate hierarchies or classifications exist: counterparty rating (Moody's vs S&P vs Fitch vs internal), product taxonomy (regulatory vs trading vs ISDA), counterparty type (legal-entity-based vs reporting-line-based), region (geographic vs booking-entity-based). In each case, the conformed dimension carries the rule explicitly, the rule has an owner, and consumers select the rule relevant to their purpose. The dimension does not have to pick a winner across legitimate variants — it just makes the variant visible.

The conformance point is subtle and worth being explicit about. What is conformed is the terminology — everyone agrees that asset_class, product_type, hierarchy_rule, and rule_owner are the columns we will use. What is not forced to conform is the values any line of business places under those columns or the hierarchy shape those values describe. Line of Business A's three-product-type view of Bond is just as valid as Line of Business B's twelve-product-type view. Both live in the dimension; consumers bind to the one they need. Conformance accommodates legitimate variance rather than suppressing it.

The Semantic Layer

Governed definitions in the BI tool — declared once, used by every dashboard.

What it is

The semantic layer sits in the BI tool (Strategy / Mosaic, Power BI, Tableau, or equivalent). It is where the analytical model is declared as metadata for consumption: which fields are dimensions vs measures, how each measure aggregates, which attributes form hierarchies, and what drill paths are valid.

It does not store data. It sits on top of the analytical model and tells the BI tool how to interpret the data when generating queries.

The four things it declares

1 — Measure aggregation rules

Every measure is tagged with its rule: Sum, Avg, Max, weighted average, semi-additive (sums over some dimensions but not others), etc. This determines what number the dashboard returns at any chosen grouping.

2 — Attribute hierarchies

Parent-child relationships between attributes: Trade rolls up to Netting Set rolls up to Agreement rolls up to Counterparty. Declares safe drill paths and constrains join behaviour.

3 — Join paths

Which physical joins connect which tables, and which path the BI tool should use when a query needs to traverse multiple tables. Avoids ambiguity when multiple paths exist.

4 — Compound metrics

Derived measures that depend on others — coverage ratios, weighted averages, regulatory ratios. Defined as formulas so they recompute correctly at any grouping the user chooses.

Diagram

Figure 3 — The semantic layer is the governed metadata bridge between physical tables and every consuming dashboard.

Why not put this logic in every dashboard?

This is the question that determines whether the semantic layer adds value or sits idle. Without it, every dashboard author has to encode aggregation rules, hierarchies, and join logic in their own dashboard. That logic drifts over time. Two dashboards reporting the same metric end up with different numbers because each author made slightly different choices.

The semantic layer centralises these decisions once. Every dashboard built on top inherits the same rules. Definitions are governed in one place, not redefined per report.

Where your reports fit

Your reports today are an early version of the semantic layer — they encode some definitions, but in the report itself rather than in a governed layer. The semantic layer takes those definitions, makes them explicit, gives them governance, and exposes them to every consuming dashboard rather than just the one report.

Why this matters

  • Without a semantic layer, dashboard numbers drift. Different reports compute the same metric differently. Reconciliation becomes a regular activity.
  • The semantic layer is the only place where complex aggregation rules (semi-additivity, weighted averages, regulatory ratios) can be declared once and trusted everywhere.
  • It is also where drill paths and governance live — meaning users can self-serve safely rather than being limited to pre-built reports.

Conformance — making the data actually comparable

A logical model only delivers value if its physical instances genuinely conform — in structure, content, and source.

What conformance really means

A logical model defines an entity — Counterparty, Security, Trade — once, with one definition of every attribute. The physical world represents that entity many times: a JSON message in a TMS feed, an XML payload from a vendor, a flattened object table in Databricks, a row in a CCR fact table. Conformance is the discipline that ensures every physical instance is genuinely an instance of the same logical entity — not just structurally, but in what its values actually mean.

Conformance is not "the column names match." Column names matching is necessary but not sufficient. Two systems can both have a counterparty_rating column and still be holding fundamentally different things if one is sourcing Moody's and the other S&P, or if one is daily-refreshed and the other is point-in-time. The conformance question is: can a consumer combine these two values and trust the result?

Three forms of conformance failure

1 — Structural conformance

The physical instance does not match the logical entity's structure. Attributes missing, types wrong, relationships not enforced. This is the surface layer and the easiest to detect — schema validation catches most of it.

2 — Content conformance

Structure is fine, but values are not comparable across sources. Different vendors, different scales, different timing, different fallback rules. Two columns share a name but do not share a meaning. Silent failure — nothing breaks; numbers are simply wrong.

3 — Encoded-content conformance

A single column carries multiple distinct concepts bundled together — colon-separated, slash-separated, free-text. The data is un-parsed and therefore un-conformed. Consumers must reverse-engineer the encoding every time, often inconsistently.

Examples grounded in current state

Example 1 — Encoded content: product_type_isda

The exposure data we have today carries a field like "InterestRate:IRSwap" — one column holding both asset class (InterestRate) and product type (IRSwap), separated by a colon. To slice exposure by asset class, every downstream consumer has to parse the string. Some get it right. Some get it wrong. The logical model would represent these as two distinct attributes: asset_class and product_type, each governed, each independently usable. Splitting it is a conformance operation, not a cosmetic one.

Example 2 — Content conformance: counterparty ratings

A vendor extract carries a ratings field with values like "A1/A+/A" — multiple agency ratings bundled with no attribution. Which is Moody's, which is S&P, which is Fitch? Is the order consistent across rows? Is the order consistent across vendors? Two downstream apps making decisions on this field can both be reading "A" and treating it as the same thing, when in fact one is using Moody's and the other S&P. The logical model would carry separate, named ratings per agency. Until the data is split and attributed, it is not conformed.

Example 3 — Source conformance: CUSIP on a trade

A trade booked in a TMS system carries a CUSIP. But where did the CUSIP come from? If Security Master held the instrument, the TMS likely pulled it from there. If Security Master didn't have it yet, the trader entered it by hand — possibly correctly, possibly not. The same column name (cusip) means very different things in those two cases. Two trades, identical in the database, with completely different data lineage and reliability. Conformance requires knowing not just what the value is but where it came from.

Example 4 — Hierarchy versions: asset class classification

Security Master holds an asset-class classification — but it holds multiple hierarchies, version A and version B, because the business looks at the same instruments through different lenses (regulatory view vs. trading desk view, for example). Both are valid. Both are "the" asset class according to whoever's asking. Conformance requires declaring which hierarchy each consumer is using and binding to it explicitly — not silently picking one.

A second worked example — collateral types as a structural conformance pattern

The asset-class example above is about classification variance: one instrument, multiple naming schemes, all referring to the same thing. Collateral introduces a different kind of conformance challenge — structural variance. The collateral entity in the CMOS data takes several physically different forms: cash, sovereign bonds, corporate bonds, equities. Each is structurally distinct — cash has no security identifier, bonds carry a maturity date that equities do not, equities carry an exchange that bonds do not. They are not classification variants of the same shape; they are different shapes that all serve the same logical role.

A natural reading is that this means five different entities, or one wide flat table with many nullable columns. Both are choices, but neither is the conformed answer. The conformed answer recognises that all of these are instances of one logical entity — Collateral Position — with sub-types that carry sub-type-specific attributes. The model captures the heterogeneity inside its structure rather than pushing it onto every consumer.

This is the same principle as before, in a different direction. Earlier on this page, conformance was framed as the difference between two sources publishing data that looks the same and two sources publishing data that means the same — with the failure mode being apparent similarity hiding semantic divergence. The collateral example extends the principle: two physical implementations of the collateral model can look different — one snowflaked into separate tables, one denormalised into a single wide table — and still mean the same, as long as they faithfully implement the same logical model. Same principle, both directions: conformance is a property of meaning, not of physical shape.

The logical domain model

The logical model declares Collateral Position as the supertype entity, with the shared core attributes every collateral position has regardless of type. Three subtype entities — Cash Collateral, Bond Collateral, Equity Collateral — carry the attributes specific to each form. The supertype/subtype relationship is mutually exclusive: a given Collateral Position is exactly one of the three sub-types.

Figure 4a — Logical domain model for collateral. This is the conformed artefact — what gets governed, signed off, and referenced by every physical implementation.

Physical option A — snowflake

The most faithful physical implementation is a snowflake: one table per entity in the logical model. The supertype dim_collateral holds shared attributes; each subtype table holds its own extensions, joined back to the supertype by a foreign-key relationship on collateral_id. A bond collateral position has one row in dim_collateral and one row in dim_collateral_bond; the equity has one row in dim_collateral and one row in dim_collateral_equity; cash has only the supertype row.

Figure 4b — Physical option A: snowflake. The supertype/subtype structure of the logical model is preserved physically. Maximum integrity, more joins for type-specific drill-down.

Physical option B — denormalised flat dimension

An alternative physical implementation collapses the supertype and all subtypes into a single wide table. Every collateral position has one row in dim_collateral_flat; type-specific columns are nullable, populated only for rows of the relevant type. A cash row has nulls in cusip, maturity_date, exchange; a bond row has nulls in exchange and market_price; an equity row has nulls in maturity_date and coupon_rate. One table, many nulls, no joins.

Figure 4c — Physical option B: denormalised flat. One table, nullable columns per sub-type. No joins for any query. Weaker integrity at the column level (the database cannot enforce "maturity_date is mandatory for bonds, forbidden for cash" — that constraint moves to application logic).

Both implementations are conformant. The choice is local engineering.

A consumer querying "total collateral value posted by counterparty X across all types" gets the same answer from either physical option. A consumer querying "all bond collateral with maturity before 2027" finds the same set of rows from either, even though the snowflake requires a join and the flat table does not. The two physical models look different. They mean the same. That equivalence is what makes them both conformant.

The choice between them is a local engineering decision driven by trade-offs that are nothing to do with conformance:

Type-specific queriesJoin supertype + subtypeSingle table read, filter on type
Database-level integrityStrong — each subtype enforces its own constraintsWeaker — type-conditional constraints live in application logic
StorageCompact — no nulls for inapplicable attributesLess compact — nullable columns for non-applicable types
Schema evolutionAdd a new subtype = new table; existing subtypes unchangedAdd a new subtype = add nullable columns to the flat table
Documentation burdenHigher — each subtype is a separate objectLower — one table, column comments carry the rules

The point is that both columns of trade-offs are real engineering considerations. Different consuming systems may legitimately resolve them differently — an OLTP system that prizes integrity may pick snowflake; an analytical mart optimised for BI scan performance may pick flat. Both can coexist in the architecture, both can be conformant, and neither is "more correct" than the other.

What is not conformant is a third system that uses a different logical model — for example, one that lumps equities and bonds together as a single "Securities" type with no further distinction, or one that classifies a money-market fund as "Cash" when the conformed model treats it as a separate sub-type. Those represent semantic divergence from the agreed model, and they break conformance regardless of how their physical tables are organised. Conformance is at the logical layer; physical implementations can vary; semantic divergence cannot.

Tying back to the asset-class example earlier on this page: that example showed classification variance — the same instrument named differently, conformed by attaching the classification rule as a dimension attribute. This example shows structural variance — different sub-types sharing one logical role, conformed by representing them as supertype-with-subtypes in the model. Both are conformance patterns, both are resolved inside the model, and both preserve the same underlying principle — that conformance is a property of meaning, not of physical shape.

What risk apps need to declare — the sourcing contract

Conformance cannot be verified without explicit declaration. For each input attribute set, every risk application needs to declare the following. This becomes the data sourcing contract for the app.

DeclarationWhat is recordedExample
Source system per attribute set Not just "TMS" but which attributes come from which source. Different attribute sets from different sources. CUSIPs from Security Master; trade economics from Elypso; valuations from VS; positions from Phoenix
Precedence / fallback rules When the primary source does not have the value, where does the application look next? Documented as an ordered chain. For CUSIP: Security Master → Elypso → Markit → Bloomberg. Fall through only if prior source returns null.
Distribution platform How the data arrives — direct connection, via a services layer (e.g. Veritas), via a data lake intermediary. Each has its own rules and possible transformations. Trade data via Veritas; reference data via direct connection; valuations via data lake snapshot
Schedule / cadence How often the data refreshes. Determines timing semantics: is this point-in-time, end-of-day, intraday, real-time? Trades: real-time; reference data: daily batch at 02:00 ET; ratings: weekly
Protocol The technical mechanism. Files, API, message stream, database direct read. Affects reliability, completeness, and replay semantics. Files (SFTP daily drop); REST API on demand; Kafka stream
Transformations applied Any logic the application applies between consuming the data and using it. Splits, joins, mappings, business rules. This is where silent conformance failures hide. Splits product_type_isda on colon; maps vendor rating to internal scale; uses hierarchy version B for asset class

Why all of this is a conformance problem, not a documentation problem

Each item above looks like documentation. It is not. Each is a commitment about meaning. Once a risk app declares "I source CUSIP from Security Master with fallback to Elypso," it has committed that the CUSIP values in its output mean exactly that — not Security Master alone, not Elypso alone, but the composite under that rule. A consumer combining this with another app's CUSIP data can now verify whether the two are conformable, or determine the work needed to make them so. Without the declaration, the consumer is guessing.

Conformance is, in practice, the difference between "two apps publishing data that looks the same" and "two apps publishing data that means the same." Only the second can be combined safely.

Why this matters

  • Without conformance, multi-app analytics are unsafe. Numbers can be added that should not be added; comparisons can be made that have no real meaning.
  • The logical model alone does not deliver conformance — it specifies the target. Conformance is achieved by physical instances declaring their sources, rules, and transformations.
  • The sourcing contract is the operational mechanism. It is what makes the logical model real in the physical world.
  • This is work the risk app teams are best placed to do — only they know where each attribute came from and what rules were applied. The data team cannot reverse-engineer it.
WORKED EXAMPLE

The same approach in a different domain — credit curves

A second worked example showing the canonical/analytical pair applied to a domain that isn't collateral. The structure carries across.

The previous four pages used CCR / Collateral as the running example. The principles described — canonical entities, dimensional models, semantic layer, conformance — are not specific to that domain. This page demonstrates the same approach applied to credit curves, the reference-data domain that sits behind every CVA calculation.

Two things are worth showing in parallel for this domain. First, the logical domain model — the canonical entities and relationships that describe what a credit curve is and how it connects to everything else. Second, the star schema — the analytical shape consumers query when they need to slice and roll up curve data. These answer different questions, but they describe the same domain. They are complementary, not alternatives.

Why this example matters. Credit curves are a reference-data domain — they describe the world rather than recording events — and the entities are interrelated through time and through indirection (a counterparty maps to a reference entity which has a curve). Modelling this domain properly is what makes downstream CVA, capital calculations, and regulatory reporting reproducible and auditable. Getting the model right here pays back across every consumer of credit risk data.

The domain — what a credit curve actually is

A credit curve describes the term structure of default risk for an issuer. It can be expressed equivalently as CDS spreads, hazard rates, or survival probabilities — each tenor along the curve carries all three numbers, derived from the same underlying market data. Curves come in several types: single-name curves built from a liquid CDS reference entity's market quotes; proxy curves built from a regression on similar names when the issuer itself has no liquid CDS; internal override curves applied via stewardship for specific cases.

A trading counterparty is not the same thing as a credit curve, but it must be mapped to one for CVA to compute. The mapping has three forms in increasing fallback order: direct match (the counterparty is itself a CDS reference entity); parent match (the counterparty inherits its ultimate parent's curve); proxy match (no CDS available anywhere, fall back to a sector / rating / region proxy). The mapping is point-in-time — today's CVA uses today's mapping, but back-testing last quarter needs last quarter's mapping — so versioning matters.

The logical domain model

The canonical entities for the credit curve domain, with their key attributes and relationships:

Figure 5a — Logical domain model for credit curves. The mapping entity is the bridge from counterparties (TD's world) to reference entities and curves (the market world). Point-in-time anchoring runs through every relationship.

What the domain model gives you

  • One definition of "curve assignment" — the mapping entity makes the relationship between counterparty, curve, recovery, and match type explicit. Without it, this lives in scattered logic across systems and drifts.
  • Explicit fallback chain — match_type records whether the curve came from a direct CDS, a parent inheritance, or a proxy. Consumers can filter on this; auditors can review it; quality measurement becomes possible.
  • Point-in-time correctness — effective_from / effective_to on the mapping, and as_of_date on every curve point, make historical reconstruction reliable. Last quarter's CVA can be reproduced.
  • Stewardship visibility — steward on the mapping names who is accountable for each assignment. Manual overrides for corporate actions and gaps in Markit-LEI mapping have an owner.
  • Reference-entity decoupling — the curve describes a reference entity, not a counterparty directly. This separation lets parent-match work cleanly: the counterparty maps to its parent's reference entity, which has the curve.

The analytical shape — the star schema

The domain model captures what credit curves are and how they relate. The star schema captures what they look like when consumers query them. There are two natural fact tables, each serving a different question.

fact_curve_points answers questions about the curves themselves: how RBC's 5Y CDS spread has moved over the last year, where the hazard-rate term structure is steepest, how a proxy curve compares to the names it's built from. Each row is one (curve, tenor, as_of_date) combination, carrying the spread, hazard rate, and survival probability.

fact_counterparty_pd answers questions about applied PDs per counterparty: what PD did CVA use for RBC at the 3Y tenor yesterday, how does RBC's PD compare to its peers, where are PDs by sector drifting. Each row is one (counterparty, tenor_bucket, as_of_date) combination, with the PD value, the LGD applied, and a foreign key back to the curve that produced it.

Figure 5b — Star schema for credit curves. Two facts at different grains share conformed dimensions, so consumers can navigate from "what curve does RBC use" to "what was its 5Y spread last week" to "what PD did CVA apply" along a single, coherent dimensional model.

Both views describe the same domain. Neither replaces the other. The logical model is the conformed artefact — what gets governed and referenced. The star schema is the analytical realisation — what consumers actually query. They are translated from one another but each carries information the other does not capture explicitly.

The conformance connection

Credit curves exhibit the same conformance patterns described on Page 4. Three quick instances:

  • Classification variance. The same counterparty can map to a single-name curve in one system and a proxy curve in another, depending on each system's data freshness and stewardship. Conformance requires declaring which mapping each consumer uses, and binding to it explicitly. This is the same pattern as the asset-class variants example.
  • Sourcing variance. The cross-reference between counterparty LEI and Markit RED code is non-trivial — some applications source it from Markit directly, some from an internal stewardship layer, some from a vendor enrichment service. The CUSIP fallback story applies in the same shape: declare what the application uses, including the fallback chain.
  • Point-in-time as a conformance property. Today's CVA uses today's mapping. Yesterday's CVA must be reconstructable from yesterday's mapping. Two systems claiming to "use the same credit curve for RBC" must mean the same thing point-in-time, not the same thing today reading from each system's current state.
The reusable point. The progression on display in this worked example — from a logical domain model, through a star schema, to the conformance considerations — applies to any risk reference domain: security master, party master, agreement reference, market data curves. The specific entities differ; the modelling moves do not. Whichever domain a team is starting from, the same three artefacts get built, in roughly the same order: the canonical entities, the dimensional realisation, and the conformance declarations that make them safe to combine across applications.
SUMMARY

How the four layers fit together

Each layer does a different job. None replaces another. Reports are a starting point — not the whole picture.

Layer What it describes Where it lives What your reports contribute
Canonical Risk concepts as entities and relationships, independent of any app Logical — reference document, governed by CDO / domain modelling Reports reveal which entities your app handles; canonical model defines them once for all apps
Analytical (Star) Measures organised by grain, surrounded by dimensions for slicing Physical — star schema tables in Databricks Reports are the measure inputs — their numeric columns become facts, their descriptive columns become dimensions
Semantic Aggregation rules, hierarchies, join paths, compound metrics Metadata in BI tool — declared once, used by every dashboard Reports' implicit definitions become explicit governed declarations
Conformance The discipline that makes physical instances genuinely conform to the logical entity Sourcing contract — declared by each risk app for each attribute set it consumes Today: implicit. Required: declared sources, fallback rules, platform, schedule, protocol, transformations
The headline message for risk app teams: the reports you produce today are valuable raw material, but they are only a fraction of what a complete risk data architecture requires. To get from reports to a governed, reusable, cross-domain risk data platform, the same content needs to be expressed in three additional ways — canonical entities, star-schema facts and dimensions, and semantic metadata — and bound together by an explicit conformance discipline. Each layer does a job the others cannot.

What this means in practice

  • For risk apps: Continue producing the calculations, but also publish the underlying measures with declared grain, dimensions, and aggregation rules — not just the formatted report. Declare your sourcing contract.
  • For the risk data team: Build the canonical model for risk in collaboration with the domain teams. Define the star schemas for each sub-domain. Implement the semantic layer in the BI tool. Maintain the sourcing contracts as governed metadata.
  • For consumers: Self-serve against the semantic layer, not the raw report outputs. Governed definitions, consistent numbers, drill-down capability — backed by verifiable conformance.
