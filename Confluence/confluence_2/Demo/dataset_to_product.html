Rough draft · How an app-generated dataset becomes a data product
From dataset to data product — the metadata wrapper
A dataset doesn't become a data product by being renamed. It becomes one when it's wrapped in the metadata that consumers depend on.
The progression
1
Entity
A business concept. No rows. No agreement yet.
↓
2
Conformed Entity
Concept with agreed definition — attributes, allowed values, meaning.
↓
3
Conformed Data Model
Design — conformed entities + relationships + rules.
↓
4
App-Generated Dataset
A physical table. Has rows. Built by the app — but the data model behind it may be hidden.
↓
5
Data Product
Same dataset — now wrapped in metadata that consumers can rely on.

💡 The metadata wrapper — visible to every consumer. Below is what must be declared, transparently, before this is a product.
Data model
What entities are in this dataset? How do they relate? What rules apply? conformed_entities, FKs, precedence, filters
Sources & lineage
What feeds this dataset? Which Contract IDs populate each entity? upstream contracts · lineage spine
Ownership
Who fixes it. Who decides what it should be. technical owner · business owner
SLA & lifecycle
When can consumers expect it? What's its current state? refresh frequency · SLA · lifecycle status · classification
Consumer description
What's this dataset for? What does each column mean? table comment · column comments · aliases · allowed values
Discovery
How do consumers find it? Where's it documented? Risk Data Catalog entry · Unity Catalog tags
The point: Calling an app-generated dataset a "data product" doesn't make it one. The promotion happens when the metadata wrapper is in place — and every layer above is transparently communicated to the business.
