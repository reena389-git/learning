00 — Context

Why this matters Without preparation, profiling becomes guessing — and guessing has been the problem all along.

A profiler can run against any CSV. But its output quality depends entirely on how prepared the input is. Junk in, more junk out. The work the application team does upstream is what separates a profiler that produces a clean contract in an hour from one that produces noise that takes a week to sift through.

Three things have to be true before the CSV reaches the profiler. The data has to be clean. The columns have to be classified. And the file has to be self-describing enough that someone who didn't write it can understand what each column represents.

If these three things are true, the profiler stops being a guessing machine and becomes a directed analyser. It produces a clean candidate contract for human review, instead of a noisy list of every column-pair functional dependency it could find. The human review step becomes minutes, not days.

What follows is the eight-step preparation pipeline an application team should follow when publishing data outputs to consumers — including the BI tool, the profiler, downstream analysts, and audit. Before the steps, a foundational concept: the column role classification, which is the single highest-leverage change you can make.

01 — Foundation

Column role classification Seven roles. Every column gets exactly one. This single change eliminates 80% of profiler noise.

Before you can profile or contract a dataset, every column needs to be classified by its role in the business. The classification tells downstream tools what to do with the column — and crucially, what NOT to do with it.

Key

Identifies a row uniquely

A primary key or alternate key. Tells the profiler "this is the grain of the table".
Examples agreement_id
counterparty_code
trade_id
"What makes this row unique?"
Foreign Key

References an entity elsewhere

A pointer to a master entity that exists in another table or another data product. Tells the profiler where joins should happen.
Examples counterparty_code → counterparty master
agreement_id → agreement master
issuer_lei → issuer master
"What other entity does this row point to?"
Classifier

Categorises the row for grouping

A categorical attribute used by the business to group, slice, or report. These are the hierarchy candidates. Low cardinality typically.
Examples regulatory_regime
counterparty_rating
agreement_type
"Does the business want to group by this?"
Property

Descriptive — never grouped on

A descriptive attribute that's not used for grouping or reporting. Never a hierarchy candidate. Profiler should ignore it for relationship analysis.
Examples primary_contact_email
comments
last_updated_by
"Is this just metadata about the row?"
Measure

A numeric value to aggregate

The quantity. Carries an implicit (or explicit) grain. Tells the profiler "this is what the business wants to sum, average, or otherwise aggregate".
Examples collateral_value
indirect_exposure
dispute_amount
"Is this a number to be aggregated?"
Audit

System columns

Load timestamps, source batch identifiers, ETL metadata. Generally ignored by consumers and the profiler.
Examples load_timestamp
source_batch_id
etl_run_id
"Is this an operational artefact, not business data?"
Derived

Computed from other columns

A value the upstream engine computed from other columns. Often shouldn't be re-aggregated naively because the math has already been applied at a specific grain.
Examples concentration_ratio
net_exposure
rwa_amount
"Is this a calculated output rather than raw input?"
Unclassified

The default if nothing else fits

If you can't classify it, flag it for review. Don't let it default into the wrong role. An unclassified column should not pass validation.
Examples anything ambiguous
"If I can't decide, who can?"
Why this is the highest-leverage step The BI tool's auto-suggestion engine doesn't know which columns are classifiers vs properties — so it proposes every plausible functional dependency as a potential hierarchy. With role classification declared upstream, the profiler only looks at classifier columns for hierarchy candidates, foreign-key columns for join candidates, and measures with declared grain. The noise disappears.
02 — The critical distinction

Classifier vs property The data alone cannot tell you which is which. Only business meaning can.

This is the distinction that's easiest to lose. Two columns in a dim that both have a one-to-many functional dependency with the primary key — in the data, they look identical. In the business, they could not be more different.

Classifier → hierarchy

regulatory_regime

Each counterparty has one regulatory_regime. There are 4 distinct values across 12 counterparties.

  • Membership language works: "MUFG is an OSFI counterparty"
  • Aggregation makes sense: "count counterparties under OSFI"
  • Time invariant: regime rarely changes
  • Used in policy: "concentration limit per regime"
  • Featured in regulatory reports

Declare as a hierarchy parent of Counterparty. Business benefits — drilling, grouping, reporting, limit setting.

Property → not a hierarchy

primary_contact_email

Each counterparty has one primary_contact_email. Possibly fewer than 12 distinct values if some are shared.

  • No membership language: "MUFG is a john@td.com counterparty" is nonsense
  • Aggregation is meaningless: "count counterparties per email"
  • Time variant: emails change with staff turnover
  • Not used in policy or reporting
  • Just an operational lookup

If profiled blindly, the data shows a functional dependency. But it's not a hierarchy — it's a property. The BI tool should never offer it as a drill or group-by.

How to tell the difference

The data shape is identical. The signal lives outside the data. Use these heuristics:

TestClassifier (hierarchy)Property (not a hierarchy)
Membership language "X is an OSFI counterparty" — feels natural "X is a 'comments=urgent' counterparty" — nonsense
Aggregation "Count counterparties by regime" — useful "Count counterparties by primary email" — pointless
Stability over time Rarely changes (years) Can change frequently (months or weeks)
Policy and reporting Drives limits, regulatory reports, KPIs Operational lookup only
Who would care Senior management, credit committee, regulator Whoever needs to send an email or note something
The reviewer's job The profiler proposes candidates. The data owner — someone who knows what the column means in the business — makes the call. The profiler cannot be left to decide on its own, because the data does not contain the answer. This is why the role classification has to be declared by the application team upstream, not inferred at profiling time.
03 — Step 1

Standardise format and metadata header Every published file ships with a sidecar describing what it is.

1

Publish a sidecar metadata file with every CSV

YAML or JSON. Same base filename, different extension.

Today these CSVs probably arrive as raw data dumps — headers in row 1, data below, nothing else. The industry standard for any published data file is a metadata header describing what the file is, who owns it, what it represents, and how to interpret it.

At minimum the sidecar declares:

  • Report name and business purpose
  • Owning team and contact
  • The grain (one row per agreement per counterparty per as-of-date)
  • The as-of-date the data represents
  • Source system, source table, calculation methodology version
  • Known quality issues or caveats

In banks this often goes further and includes BCBS 239 attestation fields — who validated it, when, against what controls.

ccr_exposure_2026_03_31.csv CSV
# the data file itself
agreement_id,counterparty_code,as_of_date,...
AGR-001,BCCU,2026-03-31,...
AGR-002,BCCU,2026-03-31,...
AGR-003,JPMC,2026-03-31,...
...
ccr_exposure_2026_03_31.yml SIDECAR
product_name: ccr_collateral_exposure
version: 2.1.0
owner: ccr_engine_team
contact: ccr-eng@td.com
purpose: daily snapshot of agreement-
  level collateral exposure
grain: one row per (agreement,
  counterparty, as_of_date)
as_of_date: 2026-03-31
source_system: CCR_ENGINE v4.2
methodology: CEM + SA-CCR hybrid
attestation:
  validated_by: j.smith
  validated_on: 2026-04-01T08:00Z
  controls: [DQ-001, DQ-002, BCBS-239]
04 — Step 2

Per-column documentation Each column gets a name, a description, a type, and a role.

2

Describe every column with its role and constraints

This is where the column role classification lives.

Each column in the CSV must be described in the sidecar. Minimum fields:

  • Column name (matching the CSV header exactly)
  • Business name (the readable version)
  • Description (one sentence on what this column represents)
  • Data type (string, decimal, date, boolean)
  • Role classification (key, foreign_key, classifier, property, measure, audit, derived)
  • Source of truth (the system or upstream table that owns this value)
  • Allowed values, if any (for enumerated fields)
  • Quality contract (nullable or not, unique or not, range constraints)
ccr_exposure_2026_03_31.yml — columns section YAML
columns:
  - name: agreement_id
    business_name: Agreement ID
    description: Unique identifier for the collateral agreement
    type: string
    role: foreign_key
    references: agreement_master.agreement_id
    nullable: false

  - name: counterparty_code
    business_name: Counterparty Code
    description: Internal code for the legal entity facing TD
    type: string
    role: foreign_key
    references: counterparty_master.counterparty_code
    nullable: false

  - name: as_of_date
    business_name: As Of Date
    description: Calculation snapshot date
    type: date
    role: key
    nullable: false

  - name: regulatory_regime
    business_name: Regulatory Regime
    description: Margin regulator governing this counterparty
    type: string
    role: classifier
    allowed_values: [OSFI, EMIR, SEC, CBIRC, JFSA, CFTC]
    nullable: false

  - name: collateral_value
    business_name: Collateral Value
    description: Market value of collateral posted, USD-equivalent
    type: decimal(18,2)
    role: measure
    unit: USD
    grain: per agreement-counterparty-date

  - name: primary_contact_email
    business_name: Primary Contact Email
    description: Email of relationship manager on TD side
    type: string
    role: property
    nullable: true
What the profiler sees When the profiler reads this sidecar, it knows immediately: regulatory_regime is a classifier candidate for hierarchy analysis. primary_contact_email is a property — skip it. collateral_value is a measure — don't look for functional dependencies from it. counterparty_code and agreement_id are foreign keys with declared references — use them for join analysis. The profiler is now directed, not blind.
05 — Step 3

Clean the data before publishing Dirty data hides real dependencies and creates false ones.

3

Normalise the data so the profiler can see it clearly

A few hours of cleanup eliminates days of profiler debugging.

Profilers detect functional dependencies in actual data. If the data is messy, the dependencies are obscured. What "clean" means in practice:

  • No mixed types in a column. Date columns hold dates, not "N/A" interleaved with dates.
  • Consistent null handling. Pick one — real null, or a documented sentinel. Not a mix of empty string, "N/A", "NULL", and actual null.
  • Stable identifier formats. Counterparty code = "MUFG" everywhere, not "MUFG" in one batch and "Mufg Bank Ltd" in the next.
  • Whitespace trimmed, case normalised on identifier columns. "MUFG " and "MUFG" should not be two different counterparty values.
  • Numbers in a single representation. Don't have $1,500,000.00 in one row and 1500000 in another.
  • ISO-8601 dates. YYYY-MM-DD or YYYY-MM-DDTHH:MM:SS. No local formats.
  • Booleans consistent. Either true/false, or 0/1, or Y/N. Pick one.
  • No summary rows at top or bottom that aren't data.
  • UTF-8 encoding, declared. No mystery Windows-1252.
06 — Step 4

Validate against the contract before publishing If validation fails, the file does not ship.

4

Run a validation pass — and fail loudly if it breaks

This is where data contracts become enforceable rather than aspirational.

Before the CSV is published to a consumer, run a validation script against the sidecar contract. The validation must check:

  • Every declared column exists in the CSV
  • No undeclared columns are present
  • Every value conforms to its declared type and constraints
  • Required columns have no nulls
  • Enumerated columns contain only declared values
  • Row count is within expected range
  • Key uniqueness holds where declared
  • Referential integrity holds for foreign keys (where the master is available)

Output is pass-fail with a breach list. Files that fail validation do not ship.

Tools commonly used: Great Expectations, Soda, dbt tests, Pandera. Pick what fits the existing platform.

Why this matters for the profiler When the profiler reads the CSV, it can trust that the data conforms to the contract. No defensive parsing. No "is this column really a decimal or sometimes a string?" handling. The profiler can focus on relationships, not data hygiene.
07 — Step 5

Declare entity references Where each foreign key points — declared, not guessed.

5

For each foreign-key column, declare its master

This is the equivalent of an ERD link, declared at the source.

For each foreign-key column, the application team declares:

  • Which master entity it references (counterparty_code → Counterparty master)
  • Where the master is published (the canonical table or data product)
  • Whether referential integrity is guaranteed

This eliminates the join-discovery work the profiler would otherwise do. The profiler doesn't have to guess "is counterparty_code a foreign key to the counterparty dim?" — it's declared.

In industry, this is supported by maintaining a master entity catalogue — a registry of canonical entities and where they live. Tools that help: OpenLineage, DataHub, Collibra, Atlan. In simpler setups, a YAML file in a shared Git repo.

references section in the sidecar YAML
references:
  - column: counterparty_code
    references_entity: counterparty
    references_product: counterparty_master
    canonical_location: uc.cdm.counterparty_master
    referential_integrity: guaranteed
    cardinality: many_to_one

  - column: agreement_id
    references_entity: agreement
    references_product: agreement_master
    canonical_location: uc.cdm.agreement_master
    referential_integrity: guaranteed
    cardinality: many_to_one
08 — Step 6

Document the calculation logic For measure columns — what does the number actually represent?

6

Specify the calculation behind every measure

For the human reviewer who comes after the profiler.

For measure columns, the team provides a calculation specification — what the number represents in business terms, what inputs were used, what methodology, what model version.

This isn't for the profiler. It's for the human reviewer and for audit. When the profiler proposes "indirect_exposure looks like a measure, what's its grain?", the calculation spec answers it.

In regulated banks, this documentation is required under BCBS 239 anyway. The difference here is making it travel with the data, not as a separate document that gets out of sync.

measure specifications in the sidecar YAML
measures:
  - column: collateral_value
    business_definition: Market value of all eligible collateral
      posted by the counterparty under this agreement, valued in USD
      using closing FX rates on as_of_date
    grain: per agreement, counterparty, as_of_date
    unit: USD
    aggregation_rules:
      across_counterparty: sum
      across_agreement: sum
      across_date: latest    # semi-additive!
    methodology: haircut-adjusted, post-eligibility-filter
    model_version: CEM v4.2
    source_inputs:
      - collateral_postings (raw)
      - eligibility_schedule (per agreement)
      - haircut_table (per collateral type)
      - fx_rates (closing, as_of_date)
This solves the semi-additive measure problem at the source Every measure carries its declared aggregation rules per dimension. When the BI tool consumes this, it knows across_date: latest — and refuses to sum collateral_value across dates. The grain enforcement happens because the data product declared it, not because the dashboard author remembered to pin a filter.
09 — Step 7

Version everything When the contract changes, consumers know.

7

Semantic versioning on the contract

major.minor.patch — and a change log.

The CSV gets versioned. The sidecar contract gets versioned. When the application team changes a column, a calculation, or a constraint, the contract version bumps. Consumers can detect the change and decide whether to re-profile, re-validate, or re-test their downstream usage.

Versioning rules:

  • Major bump for breaking changes (column removed, type changed, calculation methodology changed)
  • Minor bump for additive changes (new column, new allowed value)
  • Patch bump for cosmetic changes (description rewording, business name change)

A change log alongside the contract — what changed, when, why, who reviewed it. This becomes the audit trail.

10 — Step 8

Delivery mechanism that preserves the pair The CSV and the contract have to travel together.

8

Ensure data and contract stay paired

If they get separated, you're back where you started.

In simple environments: a shared landing zone (S3 bucket, Azure Blob container) where both files land with matching base filenames.

Better: a single container or archive (ZIP, TAR) with both files inside.

Best — Parquet or Iceberg with embedded metadata. The metadata lives inside the data file's footer or table properties. Cannot be separated. Cannot drift. Faster to read. Smaller on disk. Type-safe.

Delivery formatMetadataProsCons
CSV + sidecar YAML External Universally readable, easy to inspect Can be separated; CSV is type-unsafe
CSV + YAML in ZIP Bundled Travel together; one artifact Still type-unsafe CSV inside
Parquet with footer metadata Embedded Type-safe, fast, compact, metadata can't drift Requires data engineering literacy
Iceberg / Delta table Embedded + versioned Full versioning, time travel, schema evolution Requires a lakehouse environment
11 — Bringing it together

Worked example A complete published dataset and what the profiler does with it.

Scenario

The CCR engine publishes a daily collateral exposure report. The application team has done all eight steps. The output is:

  • ccr_exposure_2026_03_31.csv — the data file
  • ccr_exposure_2026_03_31.yml — the contract sidecar with column roles, references, measure specs, version
  • Validation has passed; the file shipped

What the profiler does when it picks up this file

  1. Reads the sidecar first. Knows the grain, the columns, the roles, the references, the measure specs.
  2. Skips properties and audit columns — no profiling needed.
  3. For classifiers (regulatory_regime, agreement_type), runs functional-dependency analysis against the keys. Confirms the declared parent-child candidates exist in the data.
  4. For foreign keys (counterparty_code, agreement_id), checks referential integrity against the declared master products. If the masters are also profiled, generates the declared dim-to-dim relationship contracts.
  5. For measures, captures the declared grain and aggregation rules as part of the output contract — no inference needed.
  6. Produces a candidate contract for the BI tool to consume, enriched with confidence indicators from the data analysis.

What used to be a multi-day reconciliation exercise — fixing the BI tool's auto-detected model by hand — becomes a 30-minute review of a clean candidate contract. Most of the work is already done upstream.

12 — Context

Where industry is going This is the data contracts / data products pattern, spreading since 2022.

This is not a novel pattern. Spotify, Airbnb, Netflix, and most large banks now publish data this way for internal consumers. The driver in regulated industries is BCBS 239 in banking and similar regulations elsewhere — you have to be able to show provenance, lineage, and definition for every number that ends up in a regulatory report.

Frameworks and tools worth knowing by name

NameWhat it isWhy it matters here
Open Data Contract Standard (ODCS) Open standard for data contract structure The most mature vendor-neutral YAML format. Increasingly adopted.
dbt + dbt tests De facto open-source toolchain for SQL transformations with tested contracts Already adopted across most modern data platforms.
Great Expectations / Soda Data validation frameworks The "enforce contract at the data layer" piece.
DataHub / OpenMetadata Open-source catalog and lineage platforms Where contracts and entity references can be registered.
Apache Iceberg, Delta Lake Table formats with built-in metadata and versioning The delivery format that solves the "stay paired" problem.
dbt MetricFlow, Cube.dev YAML-based semantic layer standards The shape the BI vendor question wants to test — does the tool consume these?

You don't need any of these specifically — what matters is the pattern. But naming them in conversations with platform and architecture teams signals you've located the work in a familiar industry context, not as a one-off ask.

13 — In summary

The ask, in order of importance What to tell the application development team.

For the development team conversation

  1. Classify every column. One of seven roles: key, foreign_key, classifier, property, measure, audit, derived. This single change eliminates 80% of profiler noise.
  2. Publish a sidecar metadata file with every output — column names, types, descriptions, allowed values, foreign-key references, calculation methodology.
  3. Clean the data before publishing — consistent types, normalised nulls, ISO dates, no mixed encodings.
  4. Validate against the contract before publishing. Don't ship anything that breaks its own declared rules.
  5. Declare foreign-key references explicitly — which master entity, where it lives, whether referential integrity is guaranteed.
  6. Specify measure semantics — grain, aggregation rules per dimension, methodology, model version.
  7. Version the contract with semantic versioning and bump on every change.
  8. Deliver as Parquet with embedded metadata if you can; CSV plus YAML if you can't.

Roughly 6–8 weeks of work for a team that has never done this; 3–4 weeks for a team that already has data engineering practice. The output is durable — it serves the profiler, the BI tool, audit, and every other downstream consumer that comes after.

This is the data product / data contracts pattern applied to risk reporting. The data architecture function defines the practice; the application team implements it; the BI tool and the profiler consume the output. Every number on every dashboard traces back to a declared, owned, versioned contract.
