Provenance, the Run, and the SHA

How an aggregated product stays explainable — the ownership boundary, the three rules, and one worked example you can trace with a finger.

Purpose — the ownership boundary of an aggregated product

When Market Risk publishes an aggregate built from many sources, two accountabilities must never blur:

The product owner (Market Risk) answers for the product: its contract, aggregation logic, conformance, coverage, timeliness. One front door for consumers.
The provenance answers for the values: a bad price from Polypath is Polypath's fault, routed there — Market Risk coordinates, never absorbs.

The rule that makes this workable: every number either names its source or names its run — and the run names its sources. A product without this is refused publication: its owner becomes a permanent help desk for other people's errors.

The three provenance rules:
1. While transformations are one-to-one (landing, typing, flattening), provenance is a row-level fact — it rides along.
2. The moment aggregation goes many-to-one, provenance re-homes to the run — the row points at the run; the run holds the input manifest.
3. The transformation logic itself is never logged as data — it lives in Git; the run records the commit SHA. Manifest + SHA + inputs = full reproducibility.

Step 2 — The aggregation run: header + input manifest + SHA

Robin's aggregate computes the book-level official PV and DV01. The execution writes two small registry rows before any output:

ops.run -- the RUN HEADER (the spine, physically) run_id VR-AGG-0402 as_of 2026-04-02 run_type OFFICIAL model BookAggregation v2.3 engine RCAPS 9.1 code_sha a41f9c2 -- Git commit of the transformation code snapshot_id EOD-NY-0402 status SUCCESS started 22:04 ended 22:11 ops.run_input -- the INPUT MANIFEST run_id input_dataset delta_version upstream_run VR-AGG-0402 gold.val_murex_ged v118 MX-EOD-0402 VR-AGG-0402 gold.val_polypath v67 PP-0402-A VR-AGG-0402 gold.val_metals v41 MT-0402 VR-AGG-0402 gold.val_mr_engine v233 VR-PRC-0402
Where are the joins and aggregation logic? Not in these tables, and not in logs — in Git, at commit a41f9c2. The manifest says exactly WHAT went in (Delta versions pin the precise rows); the SHA says exactly WHAT WAS DONE. Rerun the SHA on the manifest → the identical answer. That is reproducibility as two tables and a pointer — logging the internal join mechanics as data would be enormous, unqueried, and redundant with the code.

Step 4 — Fault triage is a query, not an investigation

A consumer challenges book_pv_usd. The triage path is mechanical:

-- row → run → manifest → owners SELECT ri.input_dataset, ri.delta_version, ri.upstream_run, bm.owner FROM gold.book_valuations v JOIN ops.run_input ri ON ri.run_id = v.run_id JOIN governance.bus_matrix bm ON bm.dataset = ri.input_dataset WHERE v.book='RATES-NY' AND v.as_of='2026-04-02'; -- → four rows, four owners. Compare each input at its pinned version: -- Polypath's P-802 revalued? → their fault, routed to them (provenance answers). -- Rollup wrong at same inputs? → rerun SHA a41f9c2 → product fault, Robin's (owner answers).
One decision splits every incident: same inputs, wrong output → the product owner; right output of wrong inputs → the provenance. The registry makes that decision a three-join query.

The middle case, for completeness

Where derivation is a small, enumerable sum (a holding = Σ of its agreement's settled movements), keep the contributing keys queryable — the relationships already do this. Where it is mass computation (VaR over thousands of sensitivities), the run manifest is the honest grain — pretending row-level provenance there just fabricates precision. Small sums keep their keys; big computations keep their runs.

Standards this example encodes: no derived product publishes without a run_id on every row · every run writes header + manifest before outputs · code referenced by SHA, never logged as data · Delta versions pin inputs · coverage notes declare exclusions ("excluded, not zero") · lineage across layers = recursive query over manifests (row → run → inputs → their runs → …).
