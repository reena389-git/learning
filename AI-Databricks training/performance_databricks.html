When the automatic operations run

None of these follow a fixed schedule you set. Some happen during your write, on your cluster; others are queued in the background on serverless compute.

  1. During the write, on your cluster

    Optimized writes reshuffle data before writing so fewer, larger files land. Always on for MERGE, UPDATE and DELETE (DBR 10.4 LTS+). For Unity Catalog managed tables, file sizing is tuned automatically on SQL warehouses and DBR 11.3 LTS+.

    Clustering on write happens only when the transaction is big enough: for UC managed tables, 64 MB with 1 clustering key up to 1 GB with 4 keys. Smaller writes are clustered later by OPTIMIZE.

  2. Right after the write succeeds, still on your cluster

    Auto compaction merges small files. It runs synchronously after the write, so it adds a little time to your job, and only touches files not already compacted. It's independent of predictive optimization.

  3. In the background, on serverless compute

    Predictive optimization identifies tables that would benefit and queues OPTIMIZE (compaction and incremental clustering), VACUUM and ANALYZE. It also collects statistics as data is written to managed tables. It's billed to your account on the serverless jobs SKU.

Does anything special have to be done?

For Unity Catalog managed tables: mostly no. Predictive optimization is on by default for accounts created on or after November 11, 2024, and Databricks planned to finish enabling older accounts by August 2026. Check rather than assume:

DESCRIBE CATALOG EXTENDED my_catalog shows whether it's enabled or inherited.

Requirements

Premium plan, a supported region, SQL warehouses or DBR 12.2 LTS+, and Unity Catalog managed tables only. External tables are skipped, so they still need your own OPTIMIZE and VACUUM jobs.

Who can switch it

Account admin for the whole account. Catalog, schema or table owners (or users with MANAGE) can override with ALTER CATALOG | SCHEMA | TABLE … ENABLE | DISABLE | INHERIT PREDICTIVE OPTIMIZATION.

Do before enabling

VACUUM keeps 7 days of old files by default. If you need longer time travel, set delta.deletedFileRetentionDuration first. Turn off your own scheduled OPTIMIZE jobs once it's running.

What it won't do

It never runs ZORDER and ignores Z-ordered files. Tables still on Z-order should move to liquid clustering to benefit.

Private networking

If storage requires private connectivity, serverless private connectivity must be configured, or operations fail with PRIVATE_LINK_SETUP_ERROR. Worth checking with your platform team.

Why it skipped a table

On DBR 18 LTS+, DESCRIBE TABLE EXTENDED … AS JSON or the Catalog Explorer History tab shows skip reasons (up to 24 h delay).

Caching

Disk cache and Delta cache are the same thing. Databricks renamed the Delta cache (also called the DBIO cache) to disk cache to avoid confusion with the Delta Lake protocol. Nothing was decommissioned. The only related change: CACHE SELECT is ignored on SQL warehouses and DBR 14.2+, replaced by an improved automatic caching algorithm.

Disk cache

Where

Copies of remote Parquet/Delta files on each worker's local SSD, in a fast intermediate format.

Triggered

Automatically on first read. Invalidated automatically when files change.

How to get it

Choose worker VMs with local SSDs; they come pre-configured. Check with spark.conf.get("spark.databricks.io.cache.enabled"). Uses at most half the SSD by default.

Who

Built in on SSD node types; You configure the VM choice.

Tunes

Repeated reads of the same data.

Spark cache

Where

Executor memory (and disk, depending on storage level).

Triggered

Manually: df.cache() / df.persist(), released with unpersist().

When to use

Reusing an expensive intermediate DataFrame several times in one job. Lost when autoscaling removes a worker.

Who

You configure in code.

SQL warehouse result cache

Where

Query results kept by the SQL warehouse.

Triggered

Automatically when the same query runs again and the underlying tables haven't changed.

Who

Built in on SQL warehouses; nothing to set.

Tunes

Dashboards and repeated BI queries.

Diagnostics: how to see what's happening

Start with the query profile or Spark UI to find the slow step, then check the table the slow step reads.

Query profile

SQL warehouses and serverless. Shows each operator's time and rows, files read vs pruned, and how much time Photon handled. The fastest way to spot a scan that skipped nothing or a skewed join.

Spark UI → SQL/DataFrame tab

Classic clusters. The query DAG shows Photon operators in orange and standard Spark operators in blue, so you can see where Photon fell back.

EXPLAIN

EXPLAIN FORMATTED for a readable plan, EXPLAIN COST for size and row estimates. Confirms join strategy (broadcast vs sort-merge), pushed-down filters and join elimination.

DESCRIBE DETAIL

File count, total size, clustering columns. Many small files relative to size means compaction isn't keeping up.

DESCRIBE HISTORY

Every write and maintenance operation with metrics (files added and removed, rows). Shows whether OPTIMIZE and VACUUM actually ran.

Statistics checks

DESCRIBE EXTENDED tbl col shows column statistics; ANALYZE TABLE tbl COMPUTE STATISTICS FOR ALL COLUMNS refreshes them manually if predictive optimization isn't on.

DESCRIBE TABLE EXTENDED … AS JSON

DBR 18 LTS+. Latest predictive optimization evaluation per operation, including why it skipped.

System tables

system.query.history for slow queries over time; system.storage.predictive_optimization_operations_history for maintenance runs and their cost; system.billing.usage to compare DBUs, e.g. Photon vs non-Photon jobs.
