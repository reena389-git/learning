1. Ingestion & streaming

1.1 Auto Loader — the full command

THE FULL COMMAND
df = (spark.readStream
      .format("cloudFiles")
      .option("cloudFiles.format", "csv")
      .option("cloudFiles.schemaLocation", "/Volumes/cat/schema/raw/transactions")
      .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
      .option("cloudFiles.inferColumnTypes", "true")
      .option("header", "true")
      .load("/Volumes/cat/raw/transactions/"))

(df.writeStream
   .option("checkpointLocation", "/Volumes/cat/checkpoints/bronze_transactions")
   .trigger(availableNow=True)
   .toTable("catalog.schema.bronze_transactions"))
Flag / clauseWhat it does
.format("cloudFiles")activates Auto Loader as the source (vs. a plain file reader)
cloudFiles.formatthe format of the SOURCE files being read: csv / json / parquet / avro
cloudFiles.schemaLocationwhere Auto Loader persists the schema it infers, across restarts
cloudFiles.schemaEvolutionModehow to react when a new column appears (see 1.4 for all 4 modes)
cloudFiles.inferColumnTypesinfer real types (int/date/etc.) instead of treating every column as string
headerwhether the source files have a header row to read column names from
checkpointLocationwhere streaming PROGRESS is tracked — this is what makes restarts resumable
trigger(availableNow=True)process everything currently sitting in the source, then STOP (vs. running forever)
.toTable(...)the target table — auto-created on first run if it doesn't exist
Example
A bank drops ~500 trade-confirmation CSVs a day into a Volume. Running the command above the first time creates bronze_transactions and loads all 500. Running it again the next day, with the SAME checkpoint location, picks up only the NEW files that landed since — because checkpointLocation remembers what was already processed.

1.2 Batch load — the full command, for contrast

THE FULL COMMAND
df_batch = (spark.read
            .option("header", "true")
            .option("inferSchema", "true")
            .csv("/Volumes/cat/raw/transactions/"))

df_batch.write.mode("overwrite").saveAsTable("catalog.schema.bronze_transactions_batch")
Flag / clauseWhat it does
spark.read (not readStream)a ONE-TIME read — no checkpoint, no memory of prior runs
inferSchemaguesses column types from the data (no persisted schema location, unlike Auto Loader)
.write.mode("overwrite")replaces the table's contents entirely on every run
Example
You run this Monday: loads 500 files. Tuesday, 500 MORE files have landed. Re-running this EXACT command re-reads all 1,000 files from scratch — overwrite plus no checkpoint means there's no concept of 'what's new'.

1.3 Checkpointing

What it does
Stores which files/versions have already been committed, so a restart resumes rather than reprocesses.
Example
Auto Loader is 60 files into a 100-file batch when the cluster crashes. The checkpoint (the folder at checkpointLocation above) recorded files 1–60 as committed. On restart, Spark resumes at file 61.

1.4 Schema evolution modes — the flag, every value

THE ONE FLAG, ALL FOUR VALUES
.option("cloudFiles.schemaEvolutionMode", "addNewColumns")    # default
.option("cloudFiles.schemaEvolutionMode", "rescue")
.option("cloudFiles.schemaEvolutionMode", "failOnNewColumns")
.option("cloudFiles.schemaEvolutionMode", "none")
Flag / clauseWhat it does
addNewColumnsa new column widens the schema; the stream restarts to pick it up; old rows get NULL for it
rescueinstead of altering the schema, new/mismatched content lands in a `_rescued_data` JSON column
failOnNewColumnsthe pipeline halts entirely until a human updates the expected schema
nonethe new column is silently ignored — its values never make it into the table
Example
A new discount_code column appears in a CSV. With addNewColumns (the flag set in 1.1's full command), the schema widens automatically and old rows backfill with NULL for that column.

1.5 _rescued_data

Example
With schemaEvolutionMode = "rescue", a row with amount: "N/A" (malformed) lands as _rescued_data = {{"amount":"N/A"}}, while the rest of that row's columns load normally.

1.6 Delta table history / time travel — the full commands

THE FULL COMMAND
DESCRIBE HISTORY catalog.schema.bronze_transactions;

SELECT * FROM catalog.schema.bronze_transactions VERSION AS OF 11;
SELECT * FROM catalog.schema.bronze_transactions TIMESTAMP AS OF '2026-09-01';
Flag / clauseWhat it does
DESCRIBE HISTORYlists every write: version, timestamp, user, operation, rows affected
VERSION AS OF nquery the table exactly as it looked at version n
TIMESTAMP AS OF tsquery the table exactly as it looked at a point in time
Example
DESCRIBE HISTORY shows version 12 was a MERGE at 3:14pm that changed 40 rows. VERSION AS OF 11 shows a row's value BEFORE that correction was applied.

1.7 Silver as a streaming table — the full command

THE FULL COMMAND
CREATE OR REFRESH STREAMING TABLE catalog.schema.silver_transactions
AS SELECT * FROM STREAM(catalog.schema.bronze_transactions);
Flag / clauseWhat it does
CREATE OR REFRESHcreate on first run; incrementally refresh on every subsequent run — same statement both times
STREAMING TABLEbacked by a stream: processes only NEW micro-batches, never reprocesses history
STREAM(bronze_transactions)treats bronze's Delta transaction log as an incrementally-readable source, not a one-time snapshot
Example
Silver has processed through bronze version 20. Bronze writes version 21 (500 new rows). Silver's next trigger asks 'what changed since version 20?' via STREAM(...) and receives exactly those 500 rows.

1.8 Update/merge logic — the full foreachBatch command

THE FULL COMMAND
def upsert_to_silver(microBatchDF, batchId):
    (DeltaTable.forName(spark, "catalog.schema.silver_customers")
        .alias("t")
        .merge(microBatchDF.alias("s"), "t.customer_id = s.customer_id")
        .whenMatchedUpdateAll()
        .whenNotMatchedInsertAll()
        .execute())

(spark.readStream.table("catalog.schema.bronze_customers")
    .writeStream
    .foreachBatch(upsert_to_silver)
    .option("checkpointLocation", "/Volumes/cat/checkpoints/silver_customers")
    .trigger(availableNow=True)
    .start())
Flag / clauseWhat it does
.foreachBatch(fn)escape hatch from pure-append streaming: hands each micro-batch to your function as a static DataFrame
.merge(...)the actual MERGE — matches on the key column(s) you specify
whenMatchedUpdateAll()existing customer_id -> UPDATE the row
whenNotMatchedInsertAll()new customer_id -> INSERT a new row
Example
A customer's address changes. A plain append would create a duplicate row. This command instead updates the existing row for that customer_id — silver always has exactly one current row per customer.

2. Data quality

2.1 Expectations — the full command, all three actions together

SQL FORM
CREATE OR REFRESH STREAMING TABLE silver_transactions (
  CONSTRAINT valid_amount   EXPECT (amount >= 0),                            -- WARN (default)
  CONSTRAINT has_customer   EXPECT (customer_id IS NOT NULL) ON VIOLATION DROP ROW,
  CONSTRAINT valid_currency EXPECT (currency IN ('USD','CAD')) ON VIOLATION FAIL UPDATE
)
AS SELECT * FROM STREAM(bronze_transactions);
PYTHON FORM (same three actions)
from pyspark import pipelines as dp

@dp.table(name="silver_transactions")
@dp.expect("valid_amount", "amount >= 0")                          # WARN
@dp.expect_or_drop("has_customer", "customer_id IS NOT NULL")      # DROP
@dp.expect_or_fail("valid_currency", "currency IN ('USD','CAD')")  # FAIL
def silver_transactions():
    return dp.read_stream("bronze_transactions")
Flag / clauseWhat it does
EXPECT (...) — no ON VIOLATION / @dp.expectWARN: row stays in the output, violation is logged as a count
ON VIOLATION DROP ROW / @dp.expect_or_dropDROP: row is removed from the output entirely
ON VIOLATION FAIL UPDATE / @dp.expect_or_failFAIL: the entire pipeline update stops on any violation
Example
A row with amount = -15 hits valid_amount (WARN): it stays in the table, logged. A row with a NULL customer_id hits has_customer (DROP): removed. A row with currency = 'EUR' hits valid_currency (FAIL): the whole pipeline run stops.

2.2 Event log — the full query

THE FULL COMMAND
SELECT * FROM event_log(TABLE(catalog.schema.your_pipeline))
WHERE event_type = 'flow_progress';
Example
Returns rows like valid_amount: passed=980, failed=20 — a COUNT, not the actual 20 rows. See 2.3 for how to capture the rows themselves.

2.3 Quarantine pattern — the full command

THE FULL COMMAND
CREATE OR REFRESH STREAMING TABLE silver_transactions_quarantine
PARTITIONED BY (is_quarantined)
AS SELECT *,
   NOT (customer_id IS NOT NULL AND amount >= 0) AS is_quarantined
FROM STREAM(bronze_transactions);

CREATE OR REFRESH MATERIALIZED VIEW silver_transactions_valid    AS SELECT * FROM silver_transactions_quarantine WHERE is_quarantined = false;
CREATE OR REFRESH MATERIALIZED VIEW silver_transactions_rejected AS SELECT * FROM silver_transactions_quarantine WHERE is_quarantined = true;
Flag / clauseWhat it does
PARTITIONED BY (is_quarantined)physically separates good/bad rows on disk, keeping every column intact
NOT (...) AS is_quarantinedcomputes the SAME condition an expectation would check, but as a column, not a gate
...WHERE is_quarantined = truethis view/table holds the FULL failing rows — every column, not a count
Example
Transaction T1004 (amount = -15) lands in silver_transactions_rejected with every original column intact — an analyst opens that table and sees the complete row, not just 'count: 1'.

2.4 Join-reject capture — the full command

THE FULL COMMAND
CREATE OR REFRESH STREAMING TABLE transactions_enriched_quarantine
AS SELECT t.*, c.customer_name,
   c.customer_name IS NULL AS is_unmatched
FROM STREAM(silver_transactions_valid) t
LEFT JOIN customers c ON t.customer_id = c.customer_id;

CREATE OR REFRESH MATERIALIZED VIEW transactions_join_rejects
AS SELECT * FROM transactions_enriched_quarantine WHERE is_unmatched = true;
Flag / clauseWhat it does
LEFT JOIN (not INNER)keeps every transaction, even ones with no matching customer — INNER would silently drop them
c.customer_name IS NULL AS is_unmatchedflags exactly which rows had no match, without losing them
Example
Transaction T1005 references customer 'C999', who doesn't exist. An INNER JOIN would make T1005 vanish with zero trace. This LEFT JOIN keeps it, flags is_unmatched = true, and it lands in transactions_join_rejects — captured, not lost.

3. Performance capability matrix — full commands first

File compaction — the full set of commands together

THE FULL COMMAND
-- session-level (applies to writes in this session)
SET spark.databricks.delta.optimizeWrite.enabled = true;
SET spark.databricks.delta.autoCompact.enabled = true;

-- table-level (persists regardless of session)
ALTER TABLE catalog.schema.t SET TBLPROPERTIES (
  'delta.autoOptimize.optimizeWrite' = 'true',
  'delta.autoOptimize.autoCompact'   = 'true',
  'delta.targetFileSize'             = '134217728'   -- 128 MB
);

-- on-demand manual compaction
OPTIMIZE catalog.schema.t;
Flag / clauseWhat it does
optimizeWrite.enabledright-sizes files DURING the write (adds a shuffle stage, targets ~128MB files)
autoCompact.enabledruns a background compaction job immediately AFTER a write succeeds
delta.targetFileSizetells Delta explicitly what 'right-sized' means for this table
OPTIMIZEon-demand, explicit bin-packing — run any time file health has degraded
Example
A streaming job writes 200 tiny 2MB files overnight. With these settings on, autoCompact rewrites them into ~3 files of ~130MB each automatically — a query that opened 200 files now opens 3.

Liquid Clustering — the full command

THE FULL COMMAND
ALTER TABLE catalog.schema.t CLUSTER BY AUTO;
-- or, to pick the columns yourself instead of letting it learn them:
ALTER TABLE catalog.schema.t CLUSTER BY (customer_id, transaction_date);
Flag / clauseWhat it does
CLUSTER BY AUTOPredictive Optimization watches real query predicates/joins and picks + evolves the clustering keys itself
CLUSTER BY (col1, col2)you name the columns explicitly instead of letting it learn them
Example
Analysts always filter WHERE customer_id = X AND transaction_date > Y. CLUSTER BY AUTO notices this pattern over time and co-locates matching rows physically, so that filter reads a handful of files instead of scanning the table.

DEPRECATED
Bloom filter indexes — shown for completeness

THE OLD COMMAND (avoid for new tables)
-- legacy syntax - do not use for new tables:
ALTER TABLE catalog.schema.t
  SET TBLPROPERTIES ('delta.bloomFilter.customer_id.enabled' = 'true');
Example
This used to speed up WHERE customer_id = 'C001' by probabilistically skipping files that definitely don't contain C001. CLUSTER BY AUTO + Predictive I/O now achieve the same file-skipping outcome without a separate index to maintain — that's why this is deprecated.

Deletion vectors — the full command

THE FULL COMMAND
ALTER TABLE catalog.schema.t SET TBLPROPERTIES ('delta.enableDeletionVectors' = 'true');

UPDATE catalog.schema.t SET status = 'CANCELLED' WHERE transaction_id = 'T1001';
Flag / clauseWhat it does
delta.enableDeletionVectorsturns on marking rows as removed instead of rewriting the whole file they live in
Example
Without this flag, that UPDATE rewrites the ENTIRE file containing T1001 — maybe 100,000 unrelated rows. With it on, Delta marks just that one row and writes a small supplemental file instead.

Table statistics for the optimizer — the full command

THE FULL COMMAND
ANALYZE TABLE catalog.schema.t COMPUTE STATISTICS FOR ALL COLUMNS;
Flag / clauseWhat it does
COMPUTE STATISTICS FOR ALL COLUMNScolumn-level row/distinct counts the query PLANNER uses for join strategy and scan order
Example
Without stats, the optimizer might guess a join order badly. After ANALYZE TABLE, it knows (for example) that customers has 5 rows and transactions has 9 — and picks the smaller table to broadcast rather than shuffle.

Data skipping — the full command

THE FULL COMMAND
ALTER TABLE catalog.schema.t SET TBLPROPERTIES ('delta.dataSkippingNumIndexedCols' = '32');
Flag / clauseWhat it does
delta.dataSkippingNumIndexedColshow many of the table's FIRST columns get automatic min/max stats collected per file (default 32)
Example
A query filters WHERE amount > 1000. If amount is within the first 32 indexed columns, Delta can skip any file whose max recorded amount is 500 — without opening it.

4. Insert performance & parallelism — the full command, worked example

THE FULL COMMAND
# check current partition count BEFORE
df.rdd.getNumPartitions()          # e.g. 2

# repartition to match cluster capacity, THEN write
df_right_sized = df.repartition(32)
df_right_sized.write.mode("overwrite").saveAsTable("catalog.schema.t")
Flag / clauseWhat it does
df.rdd.getNumPartitions()read-only check: how many parallel chunks the DataFrame is currently split into
df.repartition(32)reshuffles the DataFrame into exactly 32 partitions BEFORE the write
What 'parallelism' means here
Spark splits a DataFrame into PARTITIONS. Each partition is one TASK, and tasks run in parallel across the cluster's CORES. Too few partitions = idle cores during the write; too many tiny partitions = scheduling overhead and a swarm of tiny output files.
Example
Cluster: 8 workers x 4 cores = 32 cores total. Writing 10 GB.

Too few partitions (the default, 2, from the check above): only 2 tasks run at once — 2 cores work, 30 sit idle. Each 5GB partition takes ~60s to write, so the whole job takes ~60s, using ~6% of the cluster.

After repartition(32): each partition is ~312MB. All 32 cores work simultaneously, one task each. Each finishes in ~4s, and because they run AT ONCE, the whole write finishes in ~4–8s — a 7–10x speedup from parallelism alone, nothing else changed.

Too many (e.g. repartition(5000)): 5,000 tiny output files (a few MB each) — the small-file problem — and scheduling overhead for 5,000 tiny tasks can outweigh the parallelism gain.

5. Databricks as an operational (OLTP-style) backend

No single command to anchor this section to — it's an architecture question. Staying example-led, as confirmed.

The honest answer: not great, by design
Delta Lake / the Lakehouse is architected for OLAP — analytical queries over mostly-append, batch or micro-batch data — NOT low-latency, high-concurrency, single-row transactional writes from a live UI.

5.1 Latency

Example
A risk analyst edits one field and clicks Save. A direct UPDATE against Delta on a non-warm cluster might take 2–10+ seconds. Even a warm serverless SQL warehouse carries query-planning + transaction-log-commit overhead a row-store OLTP database (sub-10ms) doesn't have.

5.2 Concurrency — Optimistic Concurrency Control (OCC)

How Delta handles concurrent writes
No row-level locking. On commit, Delta checks whether another transaction modified the same underlying files since this one started — if so, one of them RETRIES.
Example
Two analysts correct different agreements within the same second. If their updates touch overlapping files (common in a small/hot table), one Save fails with a conflict and must retry — the UI needs its own retry logic, unlike a traditional RDBMS's row locks.

5.3 Small-file amplification

Example
500 analysts each correct 1 row over a day. Each correction produces its own small commit/file — recreating the small-file problem inside an OPERATIONAL table, forcing frequent compaction just to stay readable.

5.4 The Databricks-native answer: Lakebase

Lakebase
Databricks' managed Postgres — a real OLTP row-store, built for low-latency, high-concurrency, row-level CRUD from an application. Pattern: the UI writes to Lakebase; Zero-ETL/synced tables flow that data into Delta for analytics.
Example
The corrections UI writes to Lakebase (millisecond saves, normal row locking). A synced table replicates changes into Delta on a short lag, where dashboards, Genie spaces, and agents consume it.

5.5 When direct Delta UPDATE/MERGE from a UI IS fine

Example
Occasional, low-frequency corrections — a handful of GDPR deletes a week, a monthly reconciliation batch — are a reasonable use of Delta's UPDATE/MERGE. The concern above is HIGH-FREQUENCY, MANY-CONCURRENT-USERS traffic specifically.
