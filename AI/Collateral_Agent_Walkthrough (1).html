2. Python refreshers

2.1 Decorators — @tool

Decorator
A function that WRAPS another function to add behavior. @tool turns your function into a tool object by reading its NAME, its PARAMETERS+type-hints, and its DOCSTRING.

2.2 Variables vs strings (the bug that broke the deploy)

GOTCHA we hit
In the deploy we wrote DatabricksGenieSpace(genie_space_id='GENIE_SPACE_ID') — with QUOTES. Quotes make it the literal TEXT "GENIE_SPACE_ID", not the variable's value. So the deploy looked for a Genie space literally named 'GENIE_SPACE_ID' and failed ('For input string: ""').
The rule
GENIE_SPACE_ID (no quotes) = the VARIABLE -> its value (the real UUID). 'GENIE_SPACE_ID' (quotes) = the literal STRING. Quote literal text (like a table name); do NOT quote a variable you want the value of. Fix was to remove the quotes: genie_space_id=GENIE_SPACE_ID.

2.3 f-strings and braces

f-string
f"..." lets {{x}} insert a variable. ONE brace pair = substitute a variable. Triple-quoted f"""...""" is just a MULTI-LINE f-string (used for the multi-line SQL). In your real notebook the agent input is SINGLE braces: agent.invoke({{"messages": [{{"role":"user","content": q}}]}}) — a normal dict containing a list containing a dict. (Any doubled braces you saw earlier were an artifact of THIS document being generated by an f-string, where {{ escapes to a literal {{.)

2.4 Re-running cells — what to re-run

The rule
Re-run only the cell you changed, PLUS any downstream cells that depend on its output. %%writefile agent.py only writes the file WHEN RUN — editing its text does nothing until you execute it, and the deploy reads the FILE on disk, not your cell text. When we fixed the quotes in the LOG cell, we re-ran LOG -> REGISTER -> DEPLOY, but not agent.py (it was unchanged).

3. Routing — docstring vs system prompt (corrected)

Both are needed; different jobs
The DOCSTRING on each tool is what the model routes ON — it is the tool's 'use this when…' spec that the model matches the question against. The SYSTEM PROMPT is the routing POLICY — overall preferences and any explicit hints ('for X call ToolA; for Y call ToolB'). Docstrings alone can route; the system prompt reinforces and disambiguates. Earlier this document overstated the docstring as 'the routing logic' — the accurate statement: docstring = what it routes ON, system prompt = how it routes.
What you proved
With two tools (CollateralOperations, CorporateActions), the SAME agent routed a collateral question to the Genie tool and a name-change question to the SQL tool. Same brain, different question, different tool = a multi-tool agent.

5. The DEPLOY notebook + the UC objects it creates

File: deploy_collateral_agent. Packages the agent as a file, logs it, registers it in UC, and deploys it.

5.1 The four constructs

ConstructWhat / why
%%writefile agent.pyWrites the cell to a FILE (you ship files, not notebook variables). MLflow 'Models from Code' logs this file and replays it at serving time.
class ...(ResponsesAgent) + predict()The serving CONTRACT. Model Serving calls predict(request) on every request; it reads request.input, runs the same agent loop, returns a ResponsesAgentResponse.
ResponsesAgentRequest / ResponseStandard OBJECT shapes for input/output. Input field is input (NOT messages); output is under output (NOT choices). This is the OpenAI-COMPATIBLE format — a format standard, not the vendor.
set_model / log_model / register_model / agents.deployPoint MLflow at the servable object -> record it (declaring resources) -> promote to a governed UC object -> provision the live endpoint.
GOTCHA — calling the endpoint uses different field names than a chat model
Your agent uses the ResponsesAgent contract. So: SEND {{'input':[{{'role':'user','content':q}}]}} (not 'messages'); READ the answer at response['output'][0]['content'][0]['text'] (not 'choices'). We first got a schema error 'missing inputs [input]... extra inputs [messages]' — that told us exactly to switch 'messages' -> 'input'.

Versions live on the MODEL, not the endpoint
You specify a version only at DEPLOY time (agents.deploy(model_version=N)). When you CALL the endpoint you do NOT pass a version — the endpoint always serves whatever version is currently deployed. This lets you upgrade agents (or traffic-split) without changing any caller's code.

6. The Unity Catalog permission model

This is the heart of what we learned by deploying. A deployed agent runs with the CREATOR's identity but a SCOPED credential — it does NOT inherit your full interactive access. It needs (a) resources DECLARED at deploy time, and (b) the full grant CHAIN on the data. The risk catalog grants only BROWSE by default, so every level must be granted explicitly.

6.1 The privilege ladder (definitions)

PrivilegeLevelMeaning
BROWSECatalog/SchemaDISCOVER that it exists (metadata only). Cannot query. (This is all the risk catalog grants to users by default — one row: account users : BROWSE : CATALOG.)
USE CATALOGCatalogPass THROUGH the catalog gate to reach schemas inside. A gateway privilege — does nothing by itself.
USE SCHEMASchemaPass THROUGH the schema gate to reach tables. (Schema OWNERSHIP grants you this on your schema — but NOT USE CATALOG on the parent.)
SELECTTable/ViewActually READ the data. For a VIEW, you also need SELECT on the tables the view reads.
CREATE TABLESchemaComes with schema ownership — why table-create worked in cmos_core.
CREATE MODELSchemaA SEPARATE privilege — NOT included in schema ownership by default. Why model registration FAILED in cmos_core (only BROWSE at the catalog) and had to go to workspace.

6.1b BROWSE vs USE CATALOG — the distinction, in full

These sound similar but do very different things
BROWSE = you can see that the object exists and read its metadata (names, schemas, comments) — but you cannot query or use it. Discovery-only. Like seeing a book's title and table of contents on a shelf, but not being allowed to open it. (The risk catalog grants exactly this to account users — one row: account users : BROWSE : CATALOG.)

USE CATALOG = you can traverse INTO the catalog to reach objects inside it. A gateway/pass-through privilege. It does nothing to the data by itself — it just lets your access flow through the catalog gate to the schemas and tables below. Like a key to the building lobby: it does not open your office, it just lets you reach the floor your office is on.

Why owning the schema is not enough: UC uses a TRAVERSAL model — to reach any object you must pass every gate on the path: USE CATALOG on the catalog AND USE SCHEMA on the schema. Owning the SCHEMA gives you USE SCHEMA (and CREATE TABLE) on it — but NOT USE CATALOG on the parent catalog above it. So a schema owner can still be blocked at the catalog gate if the catalog only grants BROWSE. That is exactly what happened: you own cmos_core, but the deployed agent was stuck at the catalog gate until USE CATALOG was granted.

6.2 The three failures, one root cause

All caused by 'BROWSE-only' on the risk catalog
1) Model registration into cmos_core FAILED — needs CREATE MODEL (not granted). Went to workspace instead. 2) The deployed agent could not READ cmos_core data — needs USE CATALOG -> USE SCHEMA -> SELECT (not granted). 3) Even as schema OWNER, you lacked USE CATALOG on the parent catalog. The fix that finally worked: GRANT USE CATALOG + USE SCHEMA + SELECT on the risk catalog to the run-as principal. After that, the endpoint returned real collateral numbers.

6.3 Who to grant to — account users vs the specific principal

account users
account users = EVERY user in the Databricks account (anyone using the account). It is the broadest grant. We used it to TEST (does granting fix it? yes -> confirms a permission issue). In PRODUCTION you would NOT grant sensitive risk data to everyone — you grant to the specific run-as principal only (least privilege). So: account users = fine for learning, wrong for prod.
The grants that fixed it
GRANT USE CATALOG ON CATALOG `d4001-...` TO `<principal>`; GRANT USE SCHEMA ON SCHEMA `d4001-...`.cmos_core TO `<principal>`; GRANT SELECT ON VIEW/TABLE ... (metricview, daily_exposure, asset_holdings, agreements, fx_rates) TO `<principal>`. Declaring the tables in resources=[...] scopes the credential; the GRANTs authorize it. You need BOTH.

7. Payload table vs Experiments / Traces

They are DIFFERENT records
PAYLOAD TABLE (in Catalog, ..._AGENT_payload) = the PRODUCTION log of USER requests and responses — the external 'what went in / what came out'. Used for audit and quality review of real usage. EXPERIMENTS / TRACES (MLflow) = the INTERNAL workings of each run — the reason-act loop: which tool the agent called, arguments, tool results, model calls. Used to debug HOW the agent reasoned. Analogy: Payload table = the trip receipts (what the customer asked, what they got). Experiments = the engine telemetry (how the car actually drove each trip). Same runs, two different lenses.

9. Registering a tool as a governed Unity Catalog FUNCTION

Why register a function in UC
Registering it as a UC function turns it into a governed catalog object — exactly like a table:
  • It lives in the catalog permanently (catalog.schema.function_name).
  • It has permissions (who can execute it), lineage (what it reads), an owner.
  • Any agent, notebook, or SQL query can call it — it is a shared, governed asset.
  • The agent framework can attach it as a tool via its UC name, not inline Python.
So this is the same "promote from notebook-local to governed-and-shared" pattern as model registration — but for a function. The inline @tool version only exists inside the build notebook; the registered UC function exists independently.
Workflow: a SEPARATE, one-time setup notebook
Registering a function is one-time infrastructure (like the table-creation notebook), NOT part of the build or deploy notebooks. Run it once; afterward the function is in the catalog for everything to use. Then, in the agent notebook, you SWAP the inline tool for the registered one via UCFunctionToolkit.
When UC functions are the right tool (per Databricks docs)
Recommended specifically for STRUCTURED DATA RETRIEVAL where the query is known ahead of time and the agent supplies the parameters — exactly like CorporateActions (a SQL lookup with one parameter). For other logic, MCP servers or inline agent code are often better (faster, per-user auth).

9.1 Method A — a SQL function (recommended for a data lookup)

Simplest: pure SQL, no Python context, no warehouse id in code. The COMMENT becomes the tool description the agent reads.

CREATE OR REPLACE FUNCTION `d4001-centralus-tdvip-creditrisk`.cmos_core.corp_actions_lookup(
    entity_name STRING COMMENT 'Counterparty or issuer name to look up'
)
RETURNS TABLE(entity_old STRING, entity_new STRING, action_type STRING,
             effective_date STRING, notes STRING)
COMMENT 'Look up corporate actions (name changes, mergers) for a counterparty by name.'
RETURN
  SELECT entity_old, entity_new, action_type, effective_date, notes
  FROM `d4001-centralus-tdvip-creditrisk`.cmos_core.corporate_actions
  WHERE lower(entity_old) LIKE lower('%' || entity_name || '%')
     OR lower(entity_new) LIKE lower('%' || entity_name || '%');

9.2 Method B — a Python function (for arbitrary logic)

Via the Databricks Function Client. Rules: type hints + Google-style docstring (UC builds the signature + tool description from them), and the function must be SELF-CONTAINED (imports go INSIDE, because it runs in its own context, not your notebook).

from unitycatalog.ai.core.databricks import DatabricksFunctionClient
client = DatabricksFunctionClient()

def corp_actions_lookup_py(entity_name: str) -> str:
    """Look up corporate actions (name changes, mergers) for a counterparty.
    Args:
        entity_name: The counterparty or issuer name to look up.
    Returns:
        Matching records as text, or a 'none found' message.
    """
    from databricks.sdk import WorkspaceClient
    w = WorkspaceClient()
    sql = ("SELECT entity_old, entity_new, action_type, effective_date, notes "
           "FROM `d4001-centralus-tdvip-creditrisk`.cmos_core.corporate_actions "
           f"WHERE lower(entity_old) LIKE lower('%{entity_name}%') "
           f"   OR lower(entity_new) LIKE lower('%{entity_name}%')")
    resp = w.statement_execution.execute_statement(statement=sql, warehouse_id="YOUR_WAREHOUSE_ID")
    rows = resp.result.data_array if resp.result else None
    if not rows:
        return f"No corporate actions found for '{entity_name}'."
    return "\n".join(f"{r[0]} -> {r[1]} [{r[2]}, {r[3]}]. {r[4]}" for r in rows)

info = client.create_python_function(func=corp_actions_lookup_py,
                                     catalog="d4001-centralus-tdvip-creditrisk",
                                     schema="cmos_core", replace=True)
GOTCHA — the warehouse id
The Python function runs its SQL via the statement-execution API, which needs a real warehouse_id (SQL Warehouses -> your warehouse -> ID, or [wh.id for wh in WorkspaceClient().warehouses.list()]). The SQL function (Method A) avoids this entirely — another reason SQL is simpler for a pure lookup.

9.4 Permission to USE it

EXECUTE — the function's version of SELECT
To CALL a function you need EXECUTE on it (analogous to SELECT on a table): GRANT EXECUTE ON FUNCTION ....corp_actions_lookup TO `<principal>`;
And to CREATE the function you need CREATE FUNCTION on the schema — the cousin of CREATE MODEL. Expect the same BROWSE-only wall in cmos_core; fall back to workspace.default if denied. So the privilege family now: CREATE TABLE (ownership), CREATE MODEL (separate grant), CREATE FUNCTION (separate grant), EXECUTE (to use a function).
