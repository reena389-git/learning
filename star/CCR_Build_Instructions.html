CCR POC — Mosaic Model & Dashboard Build Instructions

TD Collateral Exposure POC · full build guide for the direct/indirect exposure dashboard · 18 May 2026

This guide takes you from loaded data to a finished, demo-ready dashboard. It has two halves: MODEL work done in the Strategy/Mosaic data model, and DASHBOARD work done in the dossier. Do the model first — the dashboard depends on it.

0   The story this dashboard tells

The dashboard: pick a counterparty, see two parallel measures, drill each down its own path.

Direct exposure is what TD loses if the counterparty itself defaults — it decomposes into the underlying trades. Indirect exposure is the risk in the collateral the counterparty has posted — it decomposes into the issuers of that collateral. The two are separate measures, never added together; they answer two different risk questions.

2   MODEL  Build the data model in Mosaic

PHASE A — Add the tables

  1. Open the model. Tables tab → Import / Add tables. Add star_dim_trade and star_fact_issuer_exposure if not already present. Confirm star_dim_legal_entity is in the model too.
  2. The model should now have: the fact, counterparty, agreement, csa_type, date, collateral_eligibility, legal_entity, trade, and issuer_exposure tables.

PHASE B — Fix the joins (the attribute spans the tables)

  1. Counterparty Code — confirm it is ONE attribute, mapped to counterparty_code on every table that has it (fact, counterparty, agreement, legal_entity, issuer_exposure). Form type Text. Lookup table = star_dim_counterparty.
  2. Agreement — one attribute, mapped to agreement_id on the fact, agreement, trade, and collateral_eligibility tables. Lookup table = star_dim_agreement. This is the join that connects trades to the rest.
  3. As-Of Date — mapped to as_of_date on the fact, date, and issuer_exposure tables. Lookup = star_dim_date.
  4. Check the Tables canvas: every table should connect through these shared attributes. No table floating unconnected.
Why trades connect: star_dim_trade has no counterparty_code — it has agreement_id. The path is trade → agreement → counterparty. As long as the Agreement attribute spans both the trade table and the agreement table, the counterparty filter flows down to trades automatically.

PHASE C — Declare the hierarchies (Relationships tab)

  1. Counterparty hierarchy. Open Counterparty Code → Relationships. Add as a child: Agreement. Open Agreement → Relationships, add as a child: Trade (the Trade attribute, keyed on trade_key).
  2. Ultimate Parent. On the legal entity attributes: Ultimate Parent Name is the parent of Legal Entity Name. (Ultimate parent is self-referencing inside star_dim_legal_entity — one legal entity row IS the parent of others.)
  3. Counterparty descriptors. Counterparty Code is parent of Counterparty Legal Name, Counterparty Rating, Organisation Type, Regulatory Regime (1:N each).
  4. Time hierarchy. Year → Quarter → Month → As-Of Date, each parent of the next. Clear any warning on the time hierarchy.
  5. Issuer attributes. No hierarchy needed — Issuer Name, Issuer Type, Issuer Rating are descriptive attributes on the issuer_exposure table. Just confirm they exist as attributes after import.

PHASE D — Create the metrics

Use Create Metric for each. Set the aggregation function as shown.

MetricDefinitionAggregation
Direct ExposureSum(base_total_exposure) from the factSum across counterparty/agreement. Semi-additive over time — for the snapshot view, filter to 2026-03-31.
Indirect ExposureSum(indirect_exposure) from star_fact_issuer_exposureSum across counterparty/issuer. Filter to 2026-03-31 to match.
Trade Exposure ContributionSum(trade_exposure_contribution) from star_dim_tradeSum. This rolls up by asset class / product and reconciles to Direct Exposure.
Trade CountCount(trade_key)Count.
Collateral ValueSum(collateral_value) from issuer_exposureSum.

PHASE E — Derived attributes for the drill breakdowns

  1. Asset Class. product_type_isda looks like InterestRate:IRSwap. Create a derived attribute Asset Class = the text before the colon (Substring / Split on product_type_isda). Values: InterestRate, Credit, Equity, ForeignExchange.
  2. Keep Product Type as the full product_type_isda — this is the second drill level under Asset Class.
  3. Declare Asset Class as the parent of Product Type in the Relationships tab, so the direct-exposure drill can go Asset Class → Product Type.

PHASE F — Validate & publish

  1. Validation tab. Probe 1: Counterparty Code + Direct Exposure (filter date 2026-03-31) — numbers vary per counterparty, no smear.
  2. Probe 2: Asset Class + Trade Exposure Contribution for one counterparty — the asset classes should sum to that counterparty's Direct Exposure.
  3. Probe 3: Counterparty Code + Indirect Exposure — only the 5 counterparties with collateral schedules show a value; that is correct.
  4. Connection mode: ensure the model is set to Live (not imported cube) so the live-update demo works.
  5. Publish.

3   DASHBOARD  Build the dossier

Three pages: a summary, a direct-exposure drill, an indirect-exposure drill. The summary links to the other two.

PAGE 1 — Counterparty Exposure Summary

  1. New dossier, new grid visualization. Title it Counterparty Exposure Summary.
  2. Rows: Ultimate Parent Name, then Counterparty Legal Name (gives the merged-cell parent grouping).
  3. Metrics: Direct Exposure, Indirect Exposure — two columns, side by side.
  4. Add a filter on As-Of Date, default to 2026-03-31, so both measures show the snapshot consistently.
  5. Conditional formatting (optional): highlight Direct Exposure cells above a threshold in red — reuses the pattern from the training model.
  6. This page is the entry point. The two measures sit here as parallel columns; the audience reads "for each counterparty, here is direct and here is indirect."

PAGE 2 — Direct Exposure: Trades

  1. New page. Grid visualization titled Direct Exposure by Trade.
  2. Rows: Asset Class, then Product Type (nested — the hierarchy you declared).
  3. Metrics: Trade Exposure Contribution, Trade Count.
  4. Add an As-Of Date filter fixed to 2026-03-31 (so it reconciles to Page 1).
  5. This page expects a Counterparty filter passed in from Page 1 — configured next.

PAGE 3 — Indirect Exposure: Issuers

  1. New page. Grid visualization titled Indirect Exposure by Issuer.
  2. Rows: Issuer Type, then Issuer Name (and Issuer Rating as a second form/column).
  3. Metrics: Indirect Exposure, Collateral Value.
  4. As-Of Date filter fixed to 2026-03-31.
  5. This page also expects the Counterparty filter passed from Page 1.

WIRING — the contextual-link drills

  1. On Page 1, right-click the grid → Create Contextual Link (or Select Target Visualizations, depending on the menu).
  2. Create a link from the Direct Exposure measure / counterparty row to Page 2. Configure it to pass the selected Counterparty as the filter. Now clicking a counterparty's direct exposure jumps to Page 2 showing only that counterparty's trades.
  3. Create a second link from the Indirect Exposure measure to Page 3, also passing the selected Counterparty.
  4. Test: on Page 1 click Goldman's Direct Exposure → Page 2 shows Goldman's trades by asset class, and the asset-class subtotals sum to Goldman's direct exposure number. Click Indirect → Page 3 shows the issuers behind Goldman's collateral.
The reconciliation moment. On Page 1, note Goldman's Direct Exposure (e.g. 41,500,000). Drill to Page 2. The Trade Exposure Contribution column, summed across asset classes, equals 41,500,000. That "it adds up" moment is the strongest part of the demo — it shows the breakdown is real, not decorative.

4   The two live demos

Live update

  1. Before the audience: on Page 1, show Goldman's Direct Exposure.
  2. In Databricks, run the live-update statement (from synthetic_data_v2.sql §4): it raises event EVT-005-0331 to 75,000,000.
  3. Refresh the dossier. Goldman's Direct Exposure updates on screen — because the model is Live.

Data masking

  1. Setup once before the demo: run the masking section (synthetic_data_v2.sql §5) — creates the control table, the mask_lei function, applies the mask to lei_code. It starts masked.
  2. Put LEI Code as a column on a grid (Page 3, or a small grid on Page 1). It shows XXX-MASKED.
  3. Live: run UPDATE demo_mask_control SET masking_on = false. Refresh the dossier — real LEI codes appear.
  4. Run the same UPDATE with true to re-mask. One statement each way, fully under your control.

5   Pre-demo checklist

  • Trade data loaded; verify query shows all VM agreements reconcile.
  • Model published, connection mode = Live.
  • All three pages built; both contextual links pass the Counterparty filter.
  • As-Of Date filter = 2026-03-31 on every page.
  • Masking applied and starting in the masked state.
  • Live-update and unmask statements open in a Databricks SQL tab, ready to run.
  • Walk the full path once: summary → direct drill → back → indirect drill.
Honest note on the data. star_fact_issuer_exposure, demo_mask_control, and the trade_exposure_contribution column are POC scaffolding — not part of the governed schema, and the trade contributions are a clean point-in-time simplification of true netting math. Fine for a POC demo; flag them as such if asked, and have them governed properly before anything goes further.
