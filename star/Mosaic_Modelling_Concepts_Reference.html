1   The two layers: joins vs. hierarchies

The single biggest source of confusion in this build was treating two different things as if they were one. Mosaic has two separate structural layers, configured in two different places, doing two different jobs.

Figure 1 — Two independent layers. Getting one right tells Mosaic nothing about the other.
The rule to remember: Joins say which tables can be combined. The hierarchy says what a level means and which level is above which. They are set in different places and do not cascade — a perfect set of joins will not populate the Relationships tab, and a perfect hierarchy will not create a join.

2   Fact–dimension joins — how they are really made

A join between a fact table and a dimension table is not drawn manually in Mosaic. It emerges automatically when one logical attribute is mapped to a matching column on both tables, and a lookup table is designated.

Figure 2 — One attribute spanning both tables + a lookup table = the join. You never draw the orange line; it is a consequence.

The four conditions for a correct join

  • One unified attribute — a single Counterparty Code, not fragments.
  • Mapped to the key column on every relevant table — fact and all dimensions.
  • A lookup table is set — the clean dimension (star_dim_counterparty), one row per counterparty. This is the master source for the attribute's values.
  • Correct form type — a string code (BCCU, GSCO) must be type Text. Typed as Number, string codes fail to resolve and show blank.
Lesson from this build: the exposure grid smeared (Bank of China's row showing JPMorgan's code) because the attribute's key mapping pointed at the wrong table — an entity-resolution OBT table rather than the clean star_dim_counterparty dimension. Fixing the lookup table fixed the smear.

3   Linking, unlinking, and the (N) numbering

The (N) numbers were a running source of confusion because the same-looking suffix means two completely different things.

What you seeWhat it meansAction
(1) next to a table mapping A harmless form / mapping-count indicator. Still one attribute. Ignore it.
(2) as part of an attribute name A genuinely separate attribute object. Mosaic auto-renamed it because the name was already taken — a real duplicate / fragment. Merge it back (see below).

Three menu options — very different effects

Figure 3 — The three menu options. Two manage linking in opposite directions; one is unrelated.
"Release from linking" did the opposite of what was wanted. It fragmented a unified attribute into a separate Counterparty Code (2). To repair: either Undo, or rename the (2) back to the original name — Mosaic detects the name collision and asks "link the attributes?" → answer Yes. Renaming to an existing name is Mosaic's built-in re-link trigger.

4   Attribute relationships — the parent-child hierarchy

The Relationships tab defines how attributes relate to each other as a hierarchy of levels. It is declared by the modeller, not discovered by profiling the data.

What declaring a relationship drives

DriverWhat it gives you
AlignmentCode and Name sit correctly on the same grid row — no smearing.
AggregationMetrics roll up to the level of the attributes on the grid.
DrillThe expand / collapse path follows the declared parent-child chain.
Efficient SQLMosaic can query the lookup table directly for higher-level views.
Declared, not profiled. Mosaic may suggest relationships at import (light structural inspection), and profiling / Validation can verify the data obeys a declared relationship — but the relationship itself is an assertion of the intended business structure. Modelling to a 10-row sample would bake in accidents of the current data.

Cardinality — and why there is no "1:1"

The relationship menu offers One-to-Many, Many-to-One, Many-to-Many — but no 1:1. This is deliberate. A parent-child relationship is about hierarchy levels. If two attributes are genuinely 1:1 they are not two levels — they are the same level, two attributes describing the same thing. Those should be modelled as forms (Section 5), not as a hierarchy link.

Figure 4 — 1:N belongs in the hierarchy; 1:1 belongs in forms. There is no 1:1 in the relationship menu by design.

5   Forms — aliases of one attribute

An attribute is a thing (Legal Entity). A form is a way of expressing that thing. One attribute can carry several forms — an ID form, a name form, an LEI form — all the same row, the same grain, just different descriptive columns.

Forms are aliases of each other. Because they belong to one attribute, forms always align perfectly on a grid — there is no join to get wrong, no smearing possible. You can display one form, another, or several side by side.

A form is a clean column — not a concatenation

✓ Correct — LEI as its own form

Form expression = the bare column lei_code. Type Text. Result: a clean, separately sortable, separately filterable LEI form sitting alongside the Name form.

✗ Wrong — concatenated string

An expression like '(' + lei_code + ') ' + name mashes two facts into one value. You lose the ability to sort or filter by LEI alone. This defeats the purpose of a form.

If the combined (LEI-GS-001) Goldman Sachs look is wanted, it is achieved by displaying two forms together on a grid — a presentation choice — never by baking a concatenation into one form. Light single-value cleanup (TRIM, UPPER) inside a form is fine; combining two different things is not.

6   Aggregation — how values roll up a hierarchy

When a value at one level rolls up to its parent, the parent's value is re-computed from its children — not copied. How it is computed depends on the measure. This is the heart of the semantic layer.

Figure 5 — The parent value is computed from its children. The function used is the measure's aggregation rule.

Three aggregation classes — every measure is one of these

ClassBehaviourExamples
Additive SUM across every dimension — counterparty, time, product, all valid. Notional, collateral posted, call amount
Semi-additive SUM across most dimensions, but not across time — across dates take the LATEST or an average (a balance, not a flow). Exposure / MtM balance, collateral balance, threshold / limit
Non-additive Never summed. Must be re-computed from components at every level. Ratios & %, threshold breach, weighted averages, most sensitivities
The trap: a dashboard that sums a ratio across child rows, or sums exposure across days, produces numbers that look plausible and are wrong. The semantic layer's job is to declare, for every measure, which class it is — and configure Strategy accordingly (aggregation function; simple vs. compound metric; per-dimension behaviour). Non-additive measures are built as compound metrics — formulas over base metrics — so they re-compute correctly at whatever level is on the grid.

7   Drill-down — the three types

"Drill-down" is not one feature. Three distinct mechanisms, with different setup and different data needs.

Figure 6 — Three drill mechanisms. Type 1 walks a hierarchy; Type 2 navigates between visuals; Type 3 exposes source rows.

Hierarchy drill vs. page-link drill — the key contrast

Hierarchy drill (Type 1)Page-link drill (Type 2)
MechanismExpand / collapse along declared levelsNavigate from one visual to another, carrying a filter
SetupAutomatic — emerges from the parent-child relationshipDeliberate — you configure the link and the filter it passes
StaysOn the same gridMoves to a different page / visual
Data needThe hierarchy declaredTrade-grain data to land on
Validation tabShows it statically (grouped grid, all expanded)Not shown — interactivity is a dossier feature
On the page-link drill: "link" does not mean a manually drawn join. The data still connects through the shared Counterparty Code attribute. The deliberate part is configuring a navigation link between two visualizations and choosing the filter context it carries. And it only works if trade-level rows actually exist — if the fact table's grain is counterparty-per-date, there may be no trade detail to drill into, and trade-grain data would need to be sourced or generated first.
Drill safety depends on aggregation (Section 6). Drilling is just moving between levels. If a measure's aggregation rule is wrong, every drilled number is wrong. Correct aggregation semantics are the precondition for trustworthy drill-down.

The thread running through all of it: the model is a layered structure — physical joins at the bottom, a logical hierarchy and forms in the middle, aggregation semantics and drill behaviour at the top. Each layer is configured in its own place and rests on the one below. The data is just what currently flows through that structure; the structure itself is declared, deliberately, by the modeller.
